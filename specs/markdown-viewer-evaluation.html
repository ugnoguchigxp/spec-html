Markdown閲覧対応案の評価

結論: 条件付きで採用を推奨

MarkdownをHTML文書と同じViewer shellで閲覧できるようにする価値は高い。ただし、機能名と仕様は「HTMLと同等の文書形式」ではなく「Markdown preview」とし、最初の段階では閲覧体験の共通化に限定する。HTMLは引き続き、semantic structure、Chart.js、inline script、厳密なlintを利用できる上位形式として残す。

Markdownから永続的なHTMLを作る機能も採用価値がある。ただし、同期される生成物ではなく、Markdownを編集可能なSpec HTMLへ移行する一方向のconversion／scaffoldとして提供する。

評価対象

ここでいう「ある程度同等」は、同じ内容を同じHTMLへ変換できることではなく、利用者が既存Viewerの主要な閲覧機能をMarkdown文書でも使えることを指す。

Markdownで目標とする閲覧機能の範囲
機能 初期対応 条件・差分
navigation、並び替え、更新日時 対応 最初のh1をtitleに使い、なければfile名へfallbackする。
light／dark theme、印刷 対応 既存のsemantic HTML向けCSSを再利用する。
相対link、画像、browser history 対応 .htmlと.mdを相互に遷移できるようにする。
見出しへのfragment link 対応 重複を考慮した決定的なheading IDが必要。
source表示 対応 変換後HTMLではなく元のMarkdownを表示し、labelも形式に合わせる。
archive／restore、live reload 対応 document pathと探索処理を拡張子非依存に近づける。
Mermaid 限定対応 mermaid指定のfenced code blockを既存integrationへ接続する。
aside、details、Chart.js、inline script 非対応 初期段階ではHTML文書を使用する。raw HTMLは既定で実行しない。
既存HTML linter／fixer／formatterとの同等性 非対応 Markdown source用の検査は別phaseで設計する。

現行実装との適合性

表示の中心は、content fileを文字列として取得し、共通stylesheetとoptional integrationを付けたiframe srcdocへ挿入する処理である。Markdownを一度HTML fragmentへ変換すれば、この後半の処理はそのまま再利用できる。

一方、次の箇所は現在.htmlをdocument identityとして扱っている。

  • content directoryとarchiveからの文書探索
  • route、content URL、document stateで使うpath検証
  • navigation titleのh1抽出とindex.html等の優先順位
  • archive／restoreの対象判定
  • lint、fix、formatの対象file解決と文書間参照検査

したがって、Markdown parserを追加するだけでは不十分である。特に、Markdown内の./other.mdを既存のclient-side navigationへ渡せないと、raw fileへ直接遷移してViewer shellから外れてしまう。

実現方式の比較

推奨設計

browser変換を採用し、Node.js側とbrowser側の両方から利用できる副作用のないMarkdown rendererを1つ設ける。rendererは少なくとも、表示用HTML fragment、最初のh1から得たtitle、heading IDを同じparse結果から生成する。navigationは同じrendererまたは同じtokenization処理からtitleを取得する。

Document model

  • documentを{ path, absolutePath, format }として扱い、formatはhtmlまたはmarkdownとする。
  • 初期対応拡張子は.html、.md、.markdownとする。
  • routeとarchiveのpath検証は許可拡張子を共有し、assetの配信許可とは分離する。
  • index、overview、readmeのnavigation優先順位は拡張子に依存させない。

Markdown dialect

初期dialectはGFM相当の一般的な記法を優先し、heading、paragraph、list、task list、blockquote、fenced code、table、strikethrough、autolink、link、imageを対象とする。通常改行を強制的なbrへ変換しない。

parserの第一候補はmarkedとする。Node.jsとbrowserの両方で利用でき、GFMの主要機能を1依存で導入できるため、閲覧MVPに適する。heading IDとMermaid fenceはcustom rendererで明示的に定義する。将来、Markdown source位置に対応した高度なlintを主要要件にする場合は、位置情報を持つASTを扱いやすいunified／remark系を再評価する。

Raw HTMLとsecurity

Markdown内のraw HTMLは初期段階では実行しない。現在のHTML文書は信頼済みsourceとしてinline scriptを実行するが、Markdown対応によって一般的なREADMEまで新たな実行対象になると、利用者が想定するtrust boundaryが広がるためである。高度なHTML表現が必要な文書は.htmlを使う。

将来raw HTMLを許可する場合

暗黙に有効化せず、明示的なoptionとsecurity modelの更新を必要とする。Markdown parserの出力が自動的に安全になるとはみなさない。

Parser候補

MarkdownからHTMLへの永続変換

結論: 独立したCLIとして条件付き採用

Viewerの内部cacheや自動buildには使わず、Markdownを起点に編集可能なSpec HTML fragmentを1回生成するmigration toolとする。閲覧時変換と同じrendererを再利用するが、生成後のHTMLは独立したsource of truthとして扱う。

閲覧時変換との役割分担

Markdown previewと永続変換の責務
観点 閲覧時変換 永続変換CLI
source of truth Markdown 変換後はHTML
生成物 memory上の一時fragment 標準出力または新規.html file
主目的 Markdownを変更せず読む HTML固有のsemantic表現へ移行し、その後編集する
再実行 source変更ごとに自動 既存HTMLへは再適用しない
lint Markdown向けruleを別途適用 生成HTMLへ既存HTML linterを適用

この分離により、Markdownの変更で手編集済みHTMLが上書きされる問題と、同じ変換処理をruntime用とbuild用に二重実装する問題を避ける。

推奨CLI

spec-html convert ./design.md --lang ja
spec-html convert ./design.md --lang ja --output ./design.html
  • --outputなしではHTML fragmentだけを標準出力し、fileを書き換えない。
  • --outputはMVPでは入力と同じdirectoryの新規.htmlだけを許可し、既存fileがあれば失敗する。
  • --langは必須とし、自動言語判定、暗黙のen、front matter依存を避ける。
  • directory一括変換、上書きoption、watch modeは初期対応しない。
  • compactな診断をstderrへ出し、標準出力のHTMLをpipe可能な状態に保つ。

同じdirectoryに同じstemの.mdと.htmlを残すとnavigation上で重複する。変換は同期workflowではないため、利用者は確認後にMarkdownをcontent root外へ移すか、明示的に整理する。converterが元Markdownを自動削除、移動、archiveすることはない。

出力contract

  • 出力はfull HTML documentではなく、<article lang="…">を唯一のrootとするSpec HTML fragmentにする。
  • CSS、navigation、html、head、bodyは生成しない。
  • raw HTMLは実行可能要素として通さず、閲覧時変換と同じsecurity policyを使う。
  • heading IDは重複と日本語を含めて決定的にし、同じ入力とoptionから同じ出力を得る。
  • relative linkとasset pathは保持する。このため、MVPのfile出力先は入力と同じdirectoryに限る。
  • 改行をLFへ揃え、既存HTML formatterと同じlayout、末尾改行へ正規化する。
  • Markdown sourceは変更しない。出力へgenerator commentや同期用metadataを埋め込まない。

自動変換できる範囲

MarkdownからSpec HTMLへ情報を失わずに移せる範囲
Markdown要素 変換方針 残る作業
heading、paragraph、list、blockquote、code 標準HTMLへ直接変換 通常はなし。h1の不足や重複は診断する。
link、image 相対URLとaltを保持 参照切れは既存linterで診断する。
task list disabled checkboxを持つlistへ変換 interactiveな状態保存は行わない。
table tableとcolumn headerのscopeまでは生成 Markdownにcaption情報がないため、既存TBL001を満たすcaptionは利用者が追加する。
Mermaid fence sourceを保持したpre.mermaidへ変換 必要ならfigureとfigcaptionへ手動で昇格する。
aside、details、Chart.js 推測して生成しない 変換後HTMLでsemantic要素とfallbackを追加する。

この差があるため、converterは一般的なMarkdownを常にlint error 0のSpec HTMLへ変換できるとは約束しない。構文的に正しく整形されたdraftを生成し、既存linterの診断を同時に返す。意味を推測してcaptionやcalloutを捏造するより、残作業を明示する方を優先する。

書込安全性

  • 入力はUTF-8の通常fileに限定し、symbolic linkを拒否する。
  • 変換後のformatとlintが完了するまで出力fileを作らない。
  • 変換中に入力内容が変わった場合はsnapshot不一致として書込を中止する。
  • 出力は排他的に新規作成し、存在確認と作成の間のraceでも既存fileを上書きしない。
  • 一時fileを使い、失敗時にpartial outputを残さないcreate専用のsafe-write処理を追加する。
  • 既存fileを更新する--forceや--overwriteは設けない。

既存commandとの統合

変換pipelineは、Markdown parse、HTML fragment生成、既存formatter、既存linterの順にする。converter自身はHTML typoのfixを行わない。生成したHTMLにconverter由来のtypoがあれば実装bugであり、fixerで隠さずtestで防ぐ。

出力後は通常のspec-html check ./specs --fix --warnings-as-errorsを使える。変換時のreportは、生成したfile、変換status、HTML lint diagnosticsを区別し、lint errorが残る場合も「draftを生成した」ことが分かるようにする。

変換機能の受入条件

  • 同じ入力、言語、parser versionからbyte単位で同じfragmentを生成する。
  • 標準出力modeではstdoutにHTML以外を混ぜず、filesystemを変更しない。
  • file出力modeでは既存target、symbolic link、入力の同時変更を安全に拒否する。
  • 生成物は常にHTML parserとformatterを通過し、構文errorを含まない。
  • lint診断がMarkdown由来の意味不足とconverterの失敗を区別できる。
  • 相対linkと画像は同じdirectoryへの出力後も同じresourceを指す。
  • raw HTML内のscriptやevent handlerが生成物で実行可能にならない。
  • 変換後HTMLを手編集しても、converterの再実行で上書きされない。
  • Node.jsとBunの対応runtimeで同じfixtureを変換できる。

段階的な導入

  1. Phase 1: Viewer MVP。 文書探索、route、navigation、archive、source labelを複数形式へ対応させ、GFM相当の基本表示、relative link、heading fragment、Mermaid fenceをbrowser testで保証する。HTMLの既存挙動は変更しない。
  2. Phase 2: 検査の最小対応。 Markdownのh1、heading順序、画像alt、local file／fragment参照をsource位置付きで検査する。HTML formatterとfixerはMarkdownを書き換えず、対象外であることをreport上で明確にする。
  3. Phase 3: 要求が確認できた拡張のみ。 footnote、callout、raw HTML opt-in、より高度なMermaid表現を個別に検討する。Chart.js用の独自Markdown記法は設けない。

永続変換CLIはshared rendererと出力contractが固まった後に追加できる。Viewer route変更とは独立して提供可能だが、別rendererを先行実装して後から統合することは避ける。

Phase 1の受入条件

  • HTMLだけの既存fixtureとbrowser testが変更前と同じ結果になる。
  • 同じdirectoryの.htmlと.mdがnavigationへ同時に表示される。
  • MarkdownのGFM table、task list、code fence、画像が既存themeで読める。
  • MarkdownからHTML、HTMLからMarkdown、Markdown同士の相対linkがViewer内で遷移する。
  • 重複見出しと日本語見出しを含むfragment linkがreloadとhistory操作後も機能する。
  • Mermaid未導入時も通常のcode blockとしてsourceを読め、導入時はdiagramを表示する。
  • source dialogが元Markdownを表示し、HTML文書では既存のSource HTML表示を維持する。
  • Markdownをarchive／restoreした後もURLと文書形式が維持される。
  • Markdown内のscriptなどのraw HTMLが実行されない。
  • Node.jsとBunの対応runtime、およびChromium／Firefox／WebKitの既存検証方針を満たす。

Phase 1で行わないこと

  • MarkdownとHTMLのround-trip変換
  • Markdown sourceの自動整形や自動修正
  • front matter、MDX、wiki link、数式、独自directiveの導入
  • code syntax highlightingの追加
  • MarkdownだけでChart.js scriptを生成する独自記法
  • GitHubのrepository contextに依存するissue参照、mention、emoji等の再現
