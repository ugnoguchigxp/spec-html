vulnWorkbench一括migrationのparity不一致・根本原因調査（2026-08-19）

結論: 現行0.1.2のmigrate --writeは実行しない

../vulnWorkbench/specへのread-only preflightは、17文書中4文書だけをcontent parity一致とし、13文書をMIG004でblockした。ただし、13文書に共通する原因はMarkdownからHTMLへの内容欠落ではない。見出しとlistのDOM取得順、table内のinline要素境界への空白挿入、formatterが長いinline codeへ加える改行と、parity比較規則の不整合である。

診断用にこの4点だけを補正して同じ生成HTMLを再比較すると、content parityは17/17件で一致した。したがって安全装置は正しくwriteを止めているが、停止根拠の大半はparity実装の偽陽性である。parity実装修正前の--write強行やblocker回避は行わない。

2026-08-20 update

whole-root前提は後続実装で変更された。READMEなどのOSS定番Markdownは組み込みで保護し、--targetでcontent root相対のdirectoryを選択できる。詳細は選択的Markdown migration実装計画を参照する。本書のparity原因分析は有効だが、全17件を一括退役させることは現在の必須条件ではない。

実装結果

working treeへDOM順fact収集、inline textの位置保持、inline codeのformatter保護を実装した。code要素のnested rangeと明示的なline breakを含むcode review後のfocused test 51件が成功し、再build後のread-only preflightはparity=17/17、errors=0、ready=trueになった。vulnWorkbench側のfile変更は0件である。

これにより本書のRC1〜RC4は実装上解消した。ただし、公開済み0.1.2には修正が含まれず、language mapとArchive taxonomyの運用判断も別途必要である。canary成功だけを根拠にmigrate --writeへ進まない。

どこでblockされるか

plannerは生成HTMLをformatした後、Markdown側とHTML側から15種類のfactを作り、各配列をJSON.stringifyした完全一致で比較する。不一致が1項目でもあればMIG004を追加し、runnerはblockerがあるplanへmutationを行わない。この制御自体は期待どおりである。

補正診断で17/17になった理由

production codeは変更せず、診断用bundleだけに次の仮補正を適用し、各文書を現行convertでformatしたHTMLと再比較した。

  1. 見出しとlistを全要素のDOM順走査からtagでfilterする。
  2. accessibleHtmlTextでDOM node境界へ空白を発明せず、nodeの出現位置どおりに連結する。
  3. inline codeは現在のrendering semanticsに合わせ、連続空白を1個へ正規化して比較する。

この補正後は、visible text、headings、code block、inline code、Mermaid、task、image、link、table、paragraph、blockquote、list、inline mark、horizontal rule、line breakの全factが17/17文書で一致した。これは現行blockが内容欠落を検出した証拠ではなく、比較器の表現差を検出した証拠である。

ただし3番目は最終仕様ではない。inline codeをverbatim dataと定義するなら、比較を緩めずformatterからcode textを保護すべきである。rendered text parityを契約にするなら、Markdown側とHTML側の双方へ同じHTML whitespace規則を適用する必要がある。

内容が保持されていても現行migrateを採用できない理由

  1. 正規手順ではwriteへ到達しない。 MIG004はerrorであり、--allow-lossyの対象ではない。回避optionもない。これは安全装置を無効化すべき状況ではなく、parity実装を修正すべき状況である。
  2. 4/17という数値は移行品質の実測値として誤解を招く。 実測したのは現行collectorの一致率であり、生成HTMLの意味保持率ではない。補正診断の17/17と、RC4のliteral差を分けて報告する必要がある。
  3. inline codeの契約が未決定である。 画面表示の同値とDOM textの完全一致のどちらを保証するかを決めないまま比較だけを緩めると、本当のcode改変を見逃す。
  4. whole-root operationである。 migrateは選択した数文書だけでなくactive Markdown全件を対象にし、commit直前にactive Markdownが0件であることを要求する。このrepositoryでMarkdownを正本として継続する判断とは両立しない。

vulnWorkbenchのArchive意味との衝突

現在のspec/.archived/には20文書があり、spec/README.mdは「完了、置換、またはactive backlogを後続計画へ移管した歴史的計画」と定義している。また「全ての構想を実装した」という意味ではないことも明記済みである。したがって、既存定義を単純に「実装済み」と読むのは正確ではない。

それでもmigrationとの衝突は残る。writeするとroot直下の15 Markdownが既存spec/.archived/へ、evidence配下の2 Markdownがspec/evidence/.archived/へ移る。そこへ追加される理由は「完了・置換・後続移管」ではなく「内容はactive HTMLへ移り、Markdown表現を正本から退役させた」である。計画lifecycleのArchiveとsource-format lifecycleのArchiveが同じdirectory名に混在する。

よって「Archiveは非active文書全般」と再定義するなら技術的には共存できるが、現在のREADMEと運用queryを更新する必要がある。計画状態とsource形式を分離したいなら、一括migrationを使わずMarkdown直接表示を継続する方が自然である。

追加で見つかったlanguage指定の問題

今回の再現commandは全生成文書へlang="ja"を設定する。少なくとも次の4文書は本文が英語主体であり、writeするなら--language-mapでenを指定する必要がある。

  • evidence/phase-42-vulnworkbench-catalog-mcp-go.md
  • evidence/phase-46-release-readiness.md
  • security-intelligence-pilot-decision-template.md
  • third-party-scanners.md

content parity factはarticle[lang]を比較しないため、この誤指定は4/17という結果に現れない。これはmigrateの欠陥ではなく呼出し設定の不足だが、実移行前に別途解消すべきaccessibility条件である。

修正方針と再採用gate

  1. 複合selectorに依存せず、headings、lists、inline marksをDOM出現順で収集する。
  2. accessibleHtmlTextはtext nodeと画像altを位置どおり連結し、必要な正規化をfactごとに明示する。
  3. inline codeをverbatim保持するかrendered whitespaceで比較するかを仕様化し、compiler、formatter、parityを同じ契約へ揃える。
  4. h2 → h3 → h2、ul → ol → ul、inline codeに隣接する日本語・句読点、print widthを超えるinline codeの回帰testを追加する。
  5. 同じvulnWorkbench corpusでmigrate --checkがparity 17/17、error 0になることを確認する。
  6. language mapとArchive taxonomyを合意し、Markdownを正本から退役させる明示判断がある場合だけ--writeを実行する。

現時点の運用推奨はMarkdown直接表示を基本とし、HTML正本化するdirectoryが明確な場合だけ--targetで選択migrationすることである。保護・target外Markdownからのincoming linkが残る場合は自動編集せずblockする。選択対象については、Markdownを正本から退役させる判断とArchive運用を引き続き承認する。

修正責任の分界

parityを通すためにvulnWorkbenchのMarkdown本文を変更しない

RC1〜RC3は有効なMarkdownを正しく比較できないspec-html側の一般的な欠陥であり、RC4もformatterとparity contractの不整合である。入力文書を並べ替える、inline codeの前後へ空白を足す、長いcodeを短くする、といった変更は診断器への迎合であり、別の文書でも再発する。

vulnWorkbench本文を変更してよいのは、migrationと独立した文書品質上の理由がある場合だけである。たとえば誤記、壊れたlink、誤った仕様、言語metadata、文書lifecycleの説明不足は入力側の責任である。変更理由が「現行MIG004を消すため」だけなら修正しない。
