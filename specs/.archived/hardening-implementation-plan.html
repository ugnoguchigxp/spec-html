重要指摘対応 Hardening 実装計画

本書は、Spec HTMLの評価で確認されたデータ安全性、HTTP配信境界、回帰検出、保守性の課題を、既存機能を壊さず段階的に改修するための実装計画を定める。各phaseは単独で検証・review・rollbackできる単位とし、先行phaseの受け入れ条件を満たすまで後続phaseへ進まない。

1. 目標

  • spec-html fix --writeが、preflight後に編集されたfileや不正なUTF-8を上書きしないようにする。
  • content root内の隠しfileと隠しdirectoryをHTTP経由で配信せず、許可していないHostを持つrequestを拒否する。
  • data lossと情報漏えいに直結する境界条件を自動testで固定し、将来の回帰をCIで検出する。
  • FormatterとFixerの安全なfile書込処理を共有し、実装差による保護漏れをなくす。
  • Node側のcoverage下限とFirefox/WebKitのsmoke testを追加し、現在の多層testを定量的に補強する。

1.1 成功状態

  • Fixerのpreflight後に対象fileの内容が変わった場合、1fileも書き換えず終了code 2で失敗する。
  • 不正なUTF-8を含むHTMLはFixerとFormatterの両方が読み込み時に拒否し、元byte列を保持する。
  • /_content/.env、/_content/.git/config、nestedな隠しpath、percent encodeされた隠しpathが配信されない。
  • default設定のserverへHost: attacker.exampleを送ると、documentやshellを返さず421になる。
  • Chromiumの全browser test、FirefoxとWebKitのsmoke test、Node側coverage threshold、package consumer testがCIで通過する。
  • npm run check、npm audit、npm pack --dry-runがclean checkoutで成功する。

4. 目標構成

4.1 安全なfile I/O

新規src/content/safe-write.tsをFormatterとFixerだけが利用する内部moduleとして追加する。format/fix固有のtarget解決、diagnostic、reportは各moduleへ残し、汎用filesystem frameworkにはしない。

safe-write moduleの最小API
API 責務 失敗条件
readUtf8Snapshot fileをfatal UTF-8で読み、absolute path、source、digestを返す。 不正UTF-8、通常file以外、読込error
assertSnapshotsUnchanged 全targetのcanonical pathと現在digestをsnapshotと照合する。 target集合、path、内容のいずれかが変化
atomicReplace modeを保持し、temporary fileをflushしてrenameし、失敗時にcleanupする。 temporary名枯渇、write、sync、chmod、renameの失敗

Result objectとsnapshot集合の関連付けは既存と同じWeakMap方式を維持する。外部から構築したresultや別runのresultを--writeへ渡した場合は拒否する。

4.2 HTTP request boundary

src/server/routes.tsのroutingより前にHostを検証し、content routeではstatic file解決前に公開policyを適用する。runtime assetとoptional integrationはpackage管理下のrootなので、content用の隠しpath policyを流用しない。

  • src/server/host-policy.tsを追加し、CLI optionから正規化済み許可hostname集合を構築する。
  • Host値はWHATWG URLとnode:netを使ってhostnameとして正規化し、user info、path、空値、複数値を拒否する。
  • loopback bindでは127.0.0.1、localhost、::1だけを許可する。
  • 具体的な非loopback hostでは、指定hostと明示的な--allowed-hostだけを許可する。
  • PUT /_spec-html/document-stateはOriginがある場合、request Hostとsame-originであることも確認する。OriginがないCLIや同一machineのHTTP clientは互換性のため許可する。

5. Phase 0: Baseline固定

  1. 現在の未コミット変更を機能単位に整理し、Fixerを含むbaseline commitをreview可能にする。
  2. clean checkoutでnpm ciとnpm run checkを実行する。
  3. 現状再現testを先に追加し、Fixer同時編集、Fixer不正UTF-8、隠しfile配信、任意Hostが修正前に失敗することを確認する。
  4. hardening実装用branchはbaseline commitから作成し、既存機能追加との差分を混ぜない。

再現testは実装を先取りせず、観測済みの危険動作だけを固定する。各testが意図した理由で失敗していることを確認してからPhase 1へ進む。

6. Phase 1: FixerとFormatterのdata safety統一

6.1 実装順

  1. Formatterのfatal UTF-8 decode、digest、snapshot照合、atomic replaceを、挙動を変えずsrc/content/safe-write.tsへ移す。
  2. Formatterの既存testを変更せず通し、抽出前後のreportとfile出力が同一であることを確認する。
  3. FixerのreadFile(..., "utf8")をreadUtf8Snapshotへ置き換える。
  4. Fixer resultとsnapshot集合を関連付け、書込開始前に全対象を再検証する。
  5. Fixer固有の重複atomicWriteを削除し、共通atomicReplaceを使う。
  6. rename途中失敗時の完了、失敗、未処理report契約をFormatterとFixerで揃える。

6.2 追加test

  • preflight後に変更対象fileを外部編集した場合、すべてのfileが未変更のまま失敗する。
  • preflight後に変更不要fileを外部編集した場合も、変更対象を含め1fileも書き込まない。
  • 対象fileが同じ名前のsymlinkへ差し替わった場合に拒否する。
  • 不正UTF-8と修正可能typoが同居しても、元byte列を保持して失敗する。
  • temporary file名が衝突した場合だけretryし、renameのEEXISTはretryしない。
  • 2file目のrename失敗時に、完了済みfileと未処理fileを正確に報告してtemporary fileを残さない。
  • file modeを保持し、変更不要fileのmtimeを更新しない。

6.3 Phase 1受け入れ条件

  • Formatterの既存出力とdiagnostic snapshotに差分がない。
  • Fixerがcontent競合、不正UTF-8、path差替えをすべて書込前に拒否する。
  • src/fix/project.tsとsrc/format/project.tsにatomic write実装が重複しない。
  • npm testとnpm run test:packが成功する。

7. Phase 2: HTTP配信境界のhardening

7.1 Content path policy

  1. resolveRequestFileへcontent専用のdenyDotSegments optionを追加する。defaultは既存runtime routeとの互換性のためfalseにする。
  2. 各segmentをdecodeした後、.から始まるsegmentがあれば存在確認前に非公開扱いにする。
  3. routes.tsの個別hidden path判定を削除し、特定の内部directory名だけを特別扱いする分岐をなくす。
  4. path traversal、slash encode、backslash encode、null byte、symlink escapeの既存拒否を維持する。

7.2 HostとOrigin policy

  1. CLIへrepeat可能な--allowed-host <hostname>を追加し、CliRunOptionsからserverへ渡す。
  2. loopback、具体host、wildcard bindごとの許可host構築をpure functionとして実装する。
  3. wildcard bindで許可hostが0件なら、server起動前にusage errorとして終了する。
  4. request handlerの最初でHostを検査し、不許可時はrouteやfileの存在を確認せず421を返す。
  5. document stateのPUTでは、存在するOriginがHostと一致しない場合に403を返す。
  6. wildcard bind時にbrowserを開くURLは、listen addressではなく最初の--allowed-hostから生成する。

7.3 追加test

HTTP境界の回帰test

7.4 Phase 2受け入れ条件

  • 観測済みの.git/config配信と任意Host受付が再現しない。
  • 通常のdocument、asset、Chart.js、Mermaid、live reloadは既存URLで動作する。
  • archive/restoreはsame-originで成功し、cross-originでは状態を変更しない。
  • READMEとCLI helpがwildcard bindの新契約を説明する。

8. Phase 3: Coverageとbrowser matrix

8.1 Vitest coverage

  1. @vitest/coverage-v8を現在のVitestと同じversion帯でdev dependencyへ追加する。
  2. vitest.config.tsへV8 coverageを設定し、src/cli、src/content、src/server、src/lint、src/format、src/fixを対象にする。
  3. DOM実行をPlaywrightが担うsrc/browserと、外部runtime連携を担うsrc/vendorはVitest coverageの分母から除外し、除外理由をconfig commentに残す。
  4. lines、statements、functions、branchesを80%へ固定し、coverage/をgitignoreへ追加する。
  5. npm testの二重実行を避け、CIではcoverage付きrunを1回だけ実行する。

8.2 FirefoxとWebKit smoke test

  1. 既存testのうち、初期表示、文書間navigation、archive更新、mobile menuをsmoke対象としてtag付けする。
  2. Chromium projectは全testを実行し、Firefox/WebKit projectはsmoke tagだけを実行する。
  3. Linux CIで3browserをinstallし、macOS/Windows jobは従来どおりNode・build・packに限定する。
  4. browser固有差異が製品仕様に影響しない場合だけtest側で吸収し、製品動作の欠落をskipで隠さない。

8.3 Phase 3受け入れ条件

  • coverage thresholdを1行でも下回る変更がCIで失敗する。
  • Chromium全件とFirefox/WebKit smokeが同じcommitで成功する。
  • CI全体が既存の15分timeout内に収まる。超える場合はtest削減ではなくjob分割を行う。

9. Phase 4: 保守性改善

このphaseは安全性修正と同じcommitに含めない。Phase 1から3の回帰testが揃った後、外部動作を変えないrefactorとして実施する。

  1. src/browser/start.tsから、frame link、archive API、print lifecycleを副作用の小さいmoduleへ抽出する。
  2. initializeViewerには状態所有、event wiring、初期route復元だけを残す。
  3. src/fix/document.tsとsrc/format/envelope.tsは、単なる行数削減を目的に分割しない。candidate生成、source range解析、変換判断の境界がtestで独立できる場合だけ抽出する。
  4. public CLI、diagnostic code、JSON schema、HTML出力、HTTP routeは変更しない。

Refactor前後でVitest、Playwright、package consumer testの結果が一致し、利用者向けchangelogを必要とする挙動差分がないことを受け入れ条件とする。

10. Phase 5: 文書・release整合

  1. READMEの日英版へHost allowlist、隠しpath非公開、trusted local HTMLの境界を反映する。
  2. CONTRIBUTINGの日英版へcoverageと3browser testのcommandを追加する。
  3. CHANGELOGのSecurityへHost validationとhidden path denialを、FixedへFixer data safetyを記録する。
  4. package tarballへ追加dependency、coverage artifact、temporary fileが混入しないことを確認する。
  5. release candidateはreview済みのclean commitからだけ作成し、publication guardは別のrelease enable変更まで維持する。

14. 非目標

  • Untrusted HTMLを安全にsandbox実行する機能は追加しない。
  • 認証、TLS、internet公開server、multi-user archive管理は実装しない。
  • 全fileの複数file transactionを実装しない。書込開始前の全件検証とfile単位atomicityを保証範囲とする。
  • Markdown変換、検索、hosted service対応をhardeningへ混ぜない。
  • coverage数値を上げるためだけの意味のないassertionや内部実装固定testを追加しない。
  • 巨大moduleを行数だけで機械的に分割しない。

15. Definition of Done

  1. P0とP1の再現testが修正後に成功し、既存testに回帰がない。
  2. FixerとFormatterが同じsafe-write基盤を利用している。
  3. 隠しcontent path、任意Host、cross-origin mutationが自動testで拒否される。
  4. coverage thresholdと3browser matrixがCIの必須checkになっている。
  5. 日英README、CONTRIBUTING、CHANGELOG、CLI helpが実装と一致する。
  6. clean checkoutから完全検証とtarball consumer testが成功する。
  7. 各taskが独立reviewされ、未完了項目や一時的なsecurity bypassが残っていない。
