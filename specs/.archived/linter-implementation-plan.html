HTML document Linter 実装計画

本書は、Spec HTMLで扱うPure HTML fragmentを静的検査し、LLMと人間へ推奨される修正を少ないtokenで伝えるLinterの実装計画を定める。標準HTMLを独自DSLへ置き換えず、機械的に判定できる欠陥と、確度の高い改善候補だけを報告する。

1. 目標

  • HTML構文、文書構造、参照、accessibility、段階的強化に関する欠陥を、Viewerで開く前に検出する。
  • 各診断を、LLMが追加調査なしで修正へ移れる短い命令形にする。
  • 同じ原因から派生する診断を抑え、LLMへ渡すcontextを小さく保つ。
  • 標準HTMLの規則を再実装せず、project固有コードを検出と整形の薄い層に留める。
  • Authoring guideのルールを自動検証可能な範囲で保護する。

1.1 成功状態

  • spec-html lint ./specsがcontent directory内のHTMLを再帰的に検査する。
  • 通常出力はfile単位にまとめられ、各問題が位置、severity、rule ID、推奨修正の1行で分かる。
  • 妥当な標準HTML要素をproject独自の許可listで制限しない。
  • docsとexamplesがerrorなしで検査を通過する。
  • 全ruleに、合格例、違反例、境界例の自動testがある。

2. Linter設計原則

  1. 標準優先: HTML Living Standardとaccessibility上の確立した要件を基準とし、独自要素や独自文法を導入しない。
  2. 最小制約: 正誤を断定できるものをerror、意味の改善を高い確度で提案できるものだけをwarningにする。
  3. 修正優先: messageは原因の長い説明ではなく、望ましいHTMLの形を命令形で示す。
  4. 一原因一診断: 構文崩れや参照元欠落から派生する二次的な診断を出さない。
  5. 決定的出力: file path、位置、rule IDの順で常に同じ並びにし、LLMが差分を比較しやすくする。
  6. 段階的強化: JavaScriptを使う表現でも、重要な内容をHTML本文から取得できることを検査する。

2.1 Severity

Severityの判定基準
表示 意味 終了code
E / error 構文違反、project契約違反、壊れた参照、明確なaccessibility欠陥。修正必須。 1
W / warning HTMLとして有効だが、より意味の明確な構造を高い確度で提案できる。既定では失敗にしない。 0

--warnings-as-errors指定時だけwarningを失敗として扱う。情報だけを出す第3のseverityは設けない。

3. LLM向け診断形式

既定のcompact形式はfile pathを一度だけ表示し、診断を1行に収める。messageは「違反している」ではなく「何へ直すか」を先に書く。 

specs/sample.html
  1:1 E DOC001 root-article — 最上位を article[lang] 1個にする
  8:3 W DOC101 section-anchor — h2を含むsectionへidを付ける
summary files=1 errors=1 warnings=1

省略がある場合だけsummary末尾へdisplayed=50 omitted=Nを追加する。detailがある診断は推奨文の後ろへ; detailとして1回だけ付ける。

3.1 1診断に含める情報

  1. content rootからの相対file path
  2. 1始まりの行と列
  3. EまたはW
  4. 変更しないrule ID
  5. 短いrule名
  6. 推奨形を示す1文
  7. 必要な場合だけ、実際の個数や未解決の参照値

一般論、成功したcheck、source全体、stack trace、同じ修正説明の反復は通常出力へ含めない。

推奨修正messageは80文字以内、detailは60文字以内、file見出しを除く診断1行は180文字以内にする。上限へ収まらない理由、違反例、推奨例はrule registryへ分離し、通常出力には含めない。

3.2 Token量を抑える規則

  • file名を診断ごとに反復せず、file単位にgroup化する。
  • code frameと詳しい理由は既定で省略し、--explain RULE_IDで要求されたruleだけ表示する。
  • 同一要素へ同じruleが複数回成立しても1件にまとめる。
  • 構文解析が信頼できないfileでは構文errorを先に出し、誤検出し得る構造ruleを実行しない。
  • 既定の最大診断数を50件とし、超過時は省略件数と--max-issues 0による全件表示方法だけを末尾に示す。
  • 問題がなければsummary files=N errors=0 warnings=0の1行だけを出す。

3.3 JSON形式

--format jsonはeditorや他toolとの連携用とし、LLMへ直接渡す用途ではcompactを推奨する。JSONはschema version、summary、diagnosticsを持ち、message文字列の解析を必要としない構造にする。 

{
  "version": 1,
  "summary": {
    "files": 1,
    "errors": 1,
    "warnings": 0,
    "displayed": 1,
    "omitted": 0
  },
  "diagnostics": [
    {
      "file": "specs/sample.html",
      "line": 1,
      "column": 1,
      "severity": "error",
      "rule": "DOC001",
      "name": "root-article",
      "message": "最上位を article[lang] 1個にする"
    }
  ]
}

3.4 Rule説明とLLM修正loop

各ruleは、通常出力に使う短い推奨文に加え、--explain専用の理由、最小の違反例、最小の推奨例を1組だけ持つ。LLMは通常、次の短いloopで修正する。

  1. compact形式で実行する。
  2. errorをfile内の上から順に修正する。
  3. 修正方法が不明なruleだけ--explain RULE_IDで確認する。
  4. 再実行して派生診断が消えたことを確認し、warningを判断する。

このloopを成立させるため、rule ID、severity、推奨文はrelease間で不用意に変更しない。

--explainの出力順は見出し、理由、NG、OKに固定する。NGとOKは各1個の最小snippetだけを表示する。 

DOC001 root-article [error]
理由: Viewerへ渡す本文fragmentの文書境界を一意にする。
NG: <h1>Title</h1>
OK: <article lang="ja"><h1>Title</h1></article>

4. Error rules

Errorは自動判定が安定し、修正しない限り文書の解釈、参照、または利用可能性が損なわれる項目に限定する。

初期releaseで有効にするerror rules

HTML002 known-element 標準HTML、SVG、MathMLにない要素を使っている。内容に合う標準要素へ置き換える。
HTML003 conforming-markup 要素、属性、親子関係が標準HTMLのcontent modelに合わない。validatorが示す標準構造へ直す。

INT002 mermaid-source pre.mermaidが空である。JavaScriptなしでも取得できるdiagram sourceを本文へ置く。

5. Warning rules

WarningはHTMLとして有効な書き方を禁止しない。意味を推測するruleは、誤検出が少ない限定的なpatternだけを対象にする。

初期releaseで有効にするwarning rules
ID Rule 検出条件と推奨形
DOC101 section-anchor h2を持つsectionにidがない。安定したdeep link用のidをsectionへ付ける。
SEM101 semantic-section article直下のdivが見出しと本文をまとめている。意味に応じてsection、aside、navなどを使う。
FIG101 visual-figure canvasまたはpre.mermaidがfigure外にある。図とcaptionをfigureでまとめる。
INT101 chart-fallback canvasと同じsectioning範囲にdata tableがない。重要な値をHTMLのtableにも置く。

div、span、pの存在だけでは警告しない。sectionやtableの使用回数も評価しない。内容の意味をLinterが断定できないためである。

6. 検査engine

標準HTMLの構文、要素metadata、source位置付きDOMにはhtml-validate APIを使用する。Spec HTML固有層は、root契約、複数fileの参照、段階的強化、診断の正規化だけを担当する。

6.1 固定する技術選択

実装者が選び直さない技術事項
項目 固定値
validator html-validateをruntime dependencyとして正確に11.3.0へ固定する。caretやtildeを付けない。
version固定理由 11.3.0はproject契約のNode.js 24以上と両立する。upgradeは新versionのengines.nodeを確認する別変更で行う。
API StaticConfigLoaderと非同期HtmlValidate.validateStringを使う。同期APIとvalidateFileは使わない。
設定 TypeScript内の固定configだけを使う。利用projectの.htmlvalidate*、ignore file、preset、inline suppressionを読み込まない。
独自検査 外部公開しないinline pluginを作り、Ruleのdom:ready eventで判定する。user向けplugin APIにはしない。
実行方式 fileをsort後に1件ずつ順次検査する。並列化とcacheは初期releaseでは行わない。
bundle scripts/build.mjsのNode buildでhtml-validateをexternalにする。Browser bundleへ含めない。

html-validate:recommendedやhtml-validate:documentは使わない。fragmentに不要なDOCTYPEやstyle上の好みまで混入させないため、次のbuiltin ruleだけを明示的に有効化する。

Configはroot: true、extends: []、elements: ["html5"]とし、表にないbuiltin ruleはすべて無効にする。標準ruleの英語messageはそのまま公開せず、表の公開IDとrules.tsの日本語推奨文へ変換する。元messageは改行を空白へ変換して60文字で切り、必要な場合だけdetailとして付ける。

6.4 Parser errorと診断の重複

  • HTML004が1件以上あるfileはHTML004だけを残し、validatorを実行しない。suppression削除後の再実行で本来の診断を出す。
  • 1fileのreportにparser-errorが1件以上あれば、そのfileはHTML001だけを残し、他のbuiltin診断、project rule、収集した参照情報を破棄する。
  • 構文errorのあるfileを参照する別fileについて、対象fragmentのREF002は出さない。先に対象fileのHTML001を直させる。
  • 診断の重複keyはfile + line + column + 公開rule IDとする。同じkeyでは最初の1件だけを残す。
  • 異なるruleが同じ位置で成立する場合は両方残す。ただしDOC001成立時はDOC002とDOC003を実行しない。

6.5 文書間参照

DOM構築時に、各fileからidと次のURL属性を収集する。

a[href]、link[href]、img[src]、script[src]、video[src]、video[poster]、audio[src]、source[src]、track[src]、iframe[src]、object[data]、SVGのimage[href]とuse[href]を初期対象とする。srcsetは初期releaseでは検査しない。

  • http:、https:、mailto:、tel:、data:、blob:と//始まりは外部参照として無視する。
  • javascript:、file:を含む上記以外のschemeはViewerのcontent参照として扱えないためREF003とする。
  • #idは現在file、相対pathは現在fileのdirectoryを基準にする。queryは存在確認から除き、fragmentはpercent decodeしてID照合する。
  • /始まり、NUL、不正percent encoding、root外へ出る..、root外を指すsymlinkはREF003とする。
  • 参照先fileがない、directoryである、または読めない場合はREF003とする。HTML fileにfragmentがあり、そのIDがない場合だけREF002とする。
  • 空のhrefとqueryだけのhrefは現在documentを指すものとしてfile存在検査を省略する。
  • href以外の対象URL属性が空の場合はREF003とする。

6.6 検査順

  1. content rootをrealpathで固定し、共通file探索でHTMLを収集する。
  2. 各fileをUTF-8で読み、HTML004を先に検査する。
  3. validateString(source, absolutePath)でfragmentを検査し、builtin診断と内部plugin診断を正規化する。
  4. parser errorのないfileからIDとURL属性を収集する。
  5. 全fileの収集完了後にREF002とREF003を解決する。
  6. 重複を除き、path、行、列、rule IDでsortして出力する。

6.7 型と関数契約

export type DiagnosticSeverity = "error" | "warning";

export type RuleId =
  | "HTML001" | "HTML002" | "HTML003" | "HTML004"
  | "DOC001" | "DOC002" | "DOC003" | "DOC004" | "DOC101"
  | "REF001" | "REF002" | "REF003"
  | "A11Y001" | "A11Y002"
  | "FIG001" | "FIG101"
  | "TBL001" | "TBL002"
  | "DET001"
  | "INT001" | "INT002" | "INT101"
  | "SEM101";

export interface LintDiagnostic {
  file: string;       // content root基準、separatorは常に "/"
  line: number;       // 1始まり
  column: number;     // 1始まり
  severity: DiagnosticSeverity;
  rule: RuleId;
  name: string;
  message: string;    // rule registryの固定推奨文
  detail?: string;    // 改行なし、最大60文字
}

export interface LintSummary {
  files: number;
  errors: number;     // 省略前の総数
  warnings: number;   // 省略前の総数
  displayed: number;
  omitted: number;
}

export interface LintResult {
  diagnostics: LintDiagnostic[]; // 未truncate、sort済み
  summary: Omit<LintSummary, "displayed" | "omitted">;
}

interface LocalReference {
  value: string;
  element: string;
  attribute: string;
  line: number;
  column: number;
}

interface DocumentFacts {
  file: string;
  ids: ReadonlySet<string>;
  references: readonly LocalReference[];
}

interface DocumentLintResult {
  diagnostics: readonly LintDiagnostic[];
  facts: DocumentFacts | null; // parser-error時はnull
}

interface SpecRuleContext {
  rule: RuleId;
  detail?: string;
}

export async function lintDocument(
  source: string,
  absolutePath: string,
  relativePath: string,
): Promise<DocumentLintResult>;
export async function lintProject(contentRoot: string): Promise<LintResult>;
export function formatCompact(result: LintResult, maxIssues: number): string;
export function formatJson(result: LintResult, maxIssues: number): string;

lintProjectは診断を返し、stdoutとstderrへ書かない。directoryがない、directoryでない、readまたはrealpathに失敗した場合は例外を投げる。Formatterだけが件数制限を適用する。

内部plugin factoryはfacts保存callbackをclosureで受け取り、spec-html/document-errors、spec-html/document-warnings、spec-html/collect-factsの3 ruleを返す。前2ruleのreportはSpecRuleContext.ruleへ公開IDを必ず設定し、converterはcontextのない内部rule診断をprogramming errorとして例外にする。

6.8 Source構成

src/
├─ content/
│  └─ documents.ts  # navigationとlintが共有するHTML探索
├─ lint/
│  ├─ document.ts    # validator設定、内部plugin、1 fragmentの検査
│  ├─ project.ts     # file読込、文書間参照、lintProject
│  ├─ diagnostics.ts # 型、sort、重複除去、formatter
│  └─ rules.ts       # rule registryとbuiltin ID mapping
└─ cli/
   ├─ entry.ts       # process.argvをmainへ渡す唯一の副作用entry
   ├─ options.ts
   └─ main.ts

tests/
├─ fixtures/lint/
└─ unit/
   ├─ lint-document.test.ts
   ├─ lint-project.test.ts
   └─ lint-diagnostics.test.ts

documents.tsは、隠しdirectory、node_modules、nav.html、symlinkを探索せず、拡張子をcase-insensitiveに判定し、POSIX形式の相対pathでsortする。現在src/server/navigation.ts内にある探索をここへ移し、navigationの表示順と除外条件を変えない。

内部pluginにはerror用、warning用、文書facts収集用の3 rule classだけを置く。公開API、user plugin、設定loader、ruleごとのfileは作らない。

7. CLI仕様

spec-html lint [directory]
spec-html lint [directory] --format compact
spec-html lint [directory] --format json
spec-html lint [directory] --warnings-as-errors
spec-html lint [directory] --max-issues 50
spec-html lint --explain DOC001
  • directoryの既定値はViewerと同じ./specsとする。
  • lintの終了code 0は成功、1はlint errorまたは--warnings-as-errorsによる失敗、2はlintの引数、filesystem、内部処理の失敗とする。
  • 外部URLは存在確認しない。構文上有効なら検査対象外とする。
  • --explainはruleの理由、違反例、推奨例を表示して終了し、通常診断へ説明を反復しない。
  • --max-issues 0は件数制限なしとする。
  • --warnings-as-errorsは終了codeだけを変え、warningの表示記号、severity、JSON値をerrorへ書き換えない。

7.1 既存CLIとの互換性

  • 先頭argumentが正確にlintの場合だけlint parserへ渡す。それ以外は現在のViewer起動parserへ渡す。
  • spec-html ./lintは引き続き./lint directoryのViewer起動として扱う。
  • 既存のspec-html [directory] [--host ...]、Viewer optionのhelp行、成功出力、失敗時の終了code 1を変更しない。root helpにはlint usageだけを追記する。
  • lintでは--host、--port、--open、--no-openを拒否する。Viewer起動ではlint専用optionを拒否する。
  • spec-html lint --helpはlint help、rootの--helpは両方のusageを表示する。--versionはroot commandだけで扱う。 
export interface CliLintOptions {
  contentRoot: string;
  format: "compact" | "json";
  warningsAsErrors: boolean;
  maxIssues: number; // 0以上の安全な整数
}

export type CliCommand =
  | { kind: "run"; options: CliRunOptions }
  | { kind: "lint"; options: CliLintOptions }
  | { kind: "explain"; rule: RuleId }
  | { kind: "help" }
  | { kind: "lint-help" }
  | { kind: "version" };

--explainはdirectory、--format、--warnings-as-errors、--max-issuesと同時指定できない。未知のformat、未知のrule ID、負数、小数、指数表記、値なしはCliUsageErrorにする。

7.2 出力channel

  • lint結果と--explainはstdoutへ出す。
  • usage、filesystem、内部errorはspec-html: prefix付きでstderrへ出す。
  • JSON形式のstdoutにはJSON document以外を混ぜない。
  • compact形式は末尾を改行1個、JSON形式はJSON.stringify(value, null, 2)と末尾改行に固定する。
  • 件数制限はsort後の先頭N件に適用し、summaryのerrorsとwarningsは省略前、displayedとomittedは省略後の値にする。

repository自身の検査には、build済みCLIを使う次のscriptを追加する。

{
  "scripts": {
    "lint:docs": "node ./dist/cli.js lint ./docs --warnings-as-errors && node ./dist/cli.js lint ./examples --warnings-as-errors"
  }
}

checkではbuild直後にlint:docsを実行し、実際に配布するCLI bundleを検証する。

10. 完了条件

  • 本書のerror ruleとwarning ruleがすべて実装され、rule IDがtestで固定されている。
  • 有効なhtml-validate builtin ruleがすべて公開rule IDへmappingされ、未知のengine rule IDを黙って捨てない。
  • 1件の診断だけで対象位置、severity、推奨修正が分かる。
  • message 80文字、detail 60文字、診断1行180文字の上限をunit testで検証し、通常出力にcode frameや成功logを含めない。
  • 壊れた1要素から同じ修正を要求する診断が連鎖しない。
  • npm run checkがLinter自身、repository文書、browser上の補完検査を含めて成功する。
  • pack testでinstallしたpackageからhtml-validateを解決でき、lintの終了code 0/1/2を再現できる。
  • as any、HTML parserの自作、正規表現による一般HTML解析、user config探索を含まない。
  • Linterを通すためだけの独自要素、必須class、必須data-*属性が導入されていない。

  • 文章内容の正しさ、十分さ、読みやすさを採点すること
  • section、table、header、footerなどの使用量を強制すること
  • div、span、pを一律禁止すること
  • 自動修正、対話UI、Viewer内の診断panelを初期releaseへ含めること
  • user定義rule、plugin、設定file、inline suppressionを初期releaseへ含めること
  • 外部URLへrequestして到達性を検査すること
  • 信頼できないHTMLを安全化するsanitizerとして扱うこと
