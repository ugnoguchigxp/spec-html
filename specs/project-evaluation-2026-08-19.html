強み

  1. 移行を強制しない。 Markdown previewとHTML conversionを分離し、利用者が文書単位で移行時期を選べる。
  2. previewとconvertの意味が揃っている。 marked、heading ID、URL policy、Mermaid処理を共有し、二重実装による差を抑えている。
  3. 書込安全性が高い。 変換は同一directoryへのcreate-onlyとし、既存file／symbolic link、入力変更、result改変、競合を拒否する。
  4. security modelが現実的である。 trusted HTMLの既存機能を維持しつつ、一般的なMarkdownをscript実行対象へ広げない設計になっている。
  5. 検証が実利用に近い。 unitだけでなく、server、browser、複数runtime、複数OS、pack後のconsumer projectまで検証している。
  6. 設計判断が保存されている。 非目標、risk、rollback、release gateまでSpec HTMLで追跡でき、将来の変更理由が分かる。

release blocker

P0: Windows CIをgreenにする

最新commitのWindows jobでは360 tests中3 testsが失敗し、libuvのfs-event.c assertionによるworker errorが2件発生した。この状態ではcross-platform対応をrelease条件として満たしていない。

  • 新規convert testが/table.htmlを期待し、Windowsの\table.htmlと一致しない。path separator非依存のassertionへ変更する。
  • fix／format testがWindowsでもPOSIX mode 0640を期待するが、実測は0666だった。POSIXだけでmode保持を検証するか、platform別contractを定義する。
  • fs-event.c assertionはrunner／Node／並列worker／watcherのどれが原因かを切り分け、再実行だけで恒常的に無視しない。
P0: 公開versionとsourceを一致させる

npm 0.1.0は2026-08-19 12:34 JSTに公開され、Markdown commitは同日16:28 JSTである。registry packageのdependenciesにはmarkedとgithub-sluggerがなく、CLI helpにもconvertがない。しかしHEADのpackage.jsonも0.1.0で、changelogは0.1.0 - Unreleasedのままである。

公開済みversionは再利用できないため、Windows CI修正後に新機能releaseを0.1.1として準備する。version更新、changelogの日付と項目分離、dry-run、publish、signed tag、GitHub release、clean consumerでのregistry install確認を一続きのrelease gateにする。

最終判断

最新commitは、Spec HTMLの弱点だった「既存Markdownを持つprojectほど試しにくい」という問題へ正面から対応しており、製品方向として採用を強く支持する。実装も、単にparserを追加するのではなく、format model、navigation、archive、source表示、security、conversion、package consumerまで一貫させている。

ただし、現時点では「導入しやすくなった」のはrepository HEADを直接使う利用者に限られる。Windows CIをgreenにし、versionを0.1.1へ進めてnpmへ公開した時点で、一般利用者についても「改善」と判定できる。release blocker解消後の再評価目安は88〜90 / 100である。
