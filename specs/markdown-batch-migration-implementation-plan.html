Markdown一括移行機能 実装計画

採用方針: 一括変換を正式な移行workflowとして実装する

既存のconvertは1文書のdraft生成として維持し、directory全体の変換、link rewrite、検証、正本切替、Archive、rollbackを担うmigrateを追加する。目標は「HTML draftを複数作ること」ではなく、「MarkdownからSpec HTMLへ安全にsource of truthを切り替えること」である。

背景と解決する問題

0.1.1ではMarkdownをViewerへ直接渡せる一方、convertは入力を残したまま単一HTMLを作る。このcontractをshell loopで複数fileへ適用しても、次の移行作業は利用者へ残る。

  • 数字から始まる見出しIDとGFM tableのdeprecatedなalign属性を解消する。
  • Markdownでcaptionを直接表せないtableへ、既存見出しtextから実際のcaptionを与える。
  • Markdown間linkと既存HTMLからMarkdownへのlinkを、変換後のHTMLへ切り替える。
  • active Markdownと同名stemのHTMLを長期間併存させず、正本を一度に切り替える。
  • 複数fileの途中失敗やprocess停止から、安全にrollbackできる記録を残す。

この不足が「Viewerは使えるが一括変換は採用しにくい」という評価の原因である。説明だけを変更せず、移行の完了条件をproduct機能として実装する。

対象探索とmapping

  1. realpathでcontent rootを固定し、通常directoryであることを確認する。
  2. 既存のfindViewerDocumentsと同じ規則でactive Markdownだけを列挙する。dot directory、.archived、node_modules、symlinkは対象外とする。
  3. 各path.mdまたはpath.markdownを同じdirectoryのpath.htmlへ写像する。
  4. 大文字小文字を正規化したtarget衝突、.mdと.markdownの同一stem、既存file、directory、symlink、nav.htmlをblockerにする。
  5. 入力sourceと既存HTMLをUTF-8で読み、path、digest、modeをsnapshotへ保存する。

Archive内の既存Markdownは移行対象に含めない。提供された評価datasetならactive 17件が対象で、既存Archive 20件はそのまま保持する。

変換規則の完成

見出しID

  • Viewerとmigrationで同じgithub-slugger結果を使い、数字始まりを変更しない。
  • HTML5で有効な空白なしIDをLinterが受理し、fragment互換性を優先する。
  • 記号だけでslugが空になる見出しはsection、section-1のように一意化する。

GFM table alignment

  • deprecatedなalign属性を出力しない。
  • markdown-align-left、markdown-align-center、markdown-align-rightを生成し、共有Viewer CSSで表示する。

GFM table caption

table tokenより前にある最も近い見出しのplain textを、実際のcaptionとして複製する。captionは既存source textだけで構成し、新しい目的、要約、値を生成しない。これにより既存TBL001を弱めずに満たす。 

<h2 id="release-status">Release status</h2>
<table>
  <caption>Release status</caption>
  …
</table>
  • TBL001の「非空caption必須」という既存contractは変更しない。
  • inline markupを含む見出しは、title抽出と同じplain textへ正規化してescapeする。
  • tableより前に見出しがないMarkdownはSpec HTMLの文書contractを満たさないため、migration blockerとする。
  • 複数tableが同じsectionにある場合、同じcaptionを共有してよい。
  • JSON reportへfile、table index、採用した見出しtextとIDを記録し、compact reportには生成caption件数を表示する。利用者は移行後に文言を詳細化できる。

link rewrite

migration mappingを全fileの変換前に確定し、文字列置換ではなくMarkdown tokenとHTML attributeの位置情報を使って書き換える。

URL別のrewrite policy
入力 扱い
./guide.md targetがmapping内なら./guide.htmlへ変更する。
../plan.markdown?view=all#phase pathだけをHTMLへ変更し、queryとfragmentをbyte単位で保持する。
#section 同一文書fragmentとして変更しない。
画像、asset、未移行file 変更しない。
http:、https:など 外部URLとして変更しない。
code block、inline code、通常text URLらしい文字列があっても変更しない。

Markdown由来HTML

MarkdownCompileOptionsへpureなlink resolverを追加し、Renderer.linkがsanitize後のlocal URLだけをmappingで解決する。Viewerと単発convertはresolverを渡さず、現在のURLを保持する。

既存HTML

html-validateのParserが返すAttributeEvent.valueLocation.offsetを再利用し、document navigationを表すa[href]とarea[href]の値だけを後方offset順で置換する。quote、indent、本文、script、codeは書き換えず、変更fileだけをformatせずにatomic replaceする。その他のattributeが移行対象Markdownを参照している場合は、意味を推測して変更せずblockerとして報告する。

path解決

  • 解決はcontent-root relativeのPOSIX pathで行い、Windows path separatorへ依存しない。
  • percent-encoded segmentはdecodeしてmapping照合し、出力時はsegment単位で再encodeする。
  • root外参照、malformed encoding、symlink escapeはblockerとして既存URL policyを弱めない。

virtual project検証

書込前に「移行後に存在するはずのproject」をmemory上へ構成する。既存lintProjectのdocument解析とreference解決を、filesystem sourceとoverlay sourceを同じinterfaceで扱える形へ分離する。

  • overlayへ生成HTMLとlink rewrite後の既存HTMLを置く。
  • active Markdown pathは移行後に存在しないものとしてreference解決する。
  • 生成予定HTMLのIDとfragmentを実fileなしで解決する。
  • 画像などのassetは現在のfilesystemで存在とcontent-root境界を検査する。
  • 生成HTMLはlint error 0件を必須にする。
  • 既存HTMLはlink rewriteの有無を問わずbaseline diagnosticと比較し、新しいerrorだけをblockerにする。既知errorをmigrationの責任で修正せず、同じdiagnosticが残ることも許可する。
  • 移行対象Markdownを指す未rewrite参照は、file種別を問わずblockerにする。

変換前後のcontent parity

lintとlinkが成功しても、本文や表の値が欠落すれば一括移行は成功ではない。source Markdownのtoken treeとformat後HTMLのparse treeからfactを独立に抽出し、意図した差分以外がないことをpreflightで確認する。converter自身の中間HTMLを期待値には使わない。

  • title、見出しlevel／ID／text、正規化したvisible textの順序を比較する。
  • listとtask状態、blockquote、code text、Mermaid source、画像src／altを比較する。
  • tableのheader、cell、alignmentを比較し、追加captionだけを許可差分にする。
  • link labelとfragmentを比較し、mappingに基づくdocument拡張子変更だけを許可する。
  • raw HTMLのliteral化とunsafe URL除去は既存security policyどおりnoticeへ記録し、黙って差分扱いから除外しない。
  • fact不一致はmigration blockerとし、該当fileとfieldをreportする。

migration lifecycle

active MarkdownがArchiveへ移った時点をsource-of-truth切替とする。ただしjournalのstateがcommittedになり、実filesystemの再検証が成功するまではmigration完了と扱わない。

lock、journal、backup

content root直下の.spec-html/migrations/を内部状態directoryとして使う。dot directoryは既存document discoveryから除外される。directory自体または構成fileがsymlink、通常file以外、所有外pathの場合は処理を拒否する。 

.spec-html/
  migrate.lock
  migrations/
    20260819T120000Z-a1b2c3/
      journal.json
      backups/
        existing-html/
          guide.html
journal schemaの要点 
interface MigrationJournal {
  version: 1;
  id: string;
  state:
    | "prepared"
    | "applying"
    | "committed"
    | "rolling-back"
    | "rolled-back"
    | "finalized";
  language: string;
  sources: Array<{
    path: string;
    outputPath: string;
    digest: string;
    archived: boolean;
  }>;
  creates: Array<{
    path: string;
    digest: string;
    applied: boolean;
  }>;
  replacements: Array<{
    path: string;
    beforeDigest: string;
    afterDigest: string;
    backupPath: string;
    applied: boolean;
  }>;
}
  • migration IDはUTC時刻と暗号学的random suffixから生成し、testでは注入可能にする。
  • journalとbackupをsyncした後にのみcontent mutationを開始する。
  • 各operationの前後にstateを更新し、process停止後はdigestと実在状態から曖昧なoperationを照合する。
  • migrate.lockは排他的createで取得し、別processの同時migrationを拒否する。
  • ViewerのArchive mutationも共通content-mutation lockを確認し、migration中の移動を拒否する。
  • committedまたはfinalizedのmanifestにsource pathがある間、そのsourceはmigration管理下とし、Viewerからの個別Restoreを拒否する。復元はmigration単位の--rollbackだけで行う。
  • --finalizeは移行後に編集されたHTMLもそのまま採用し、backup payloadだけを削除する。state、migration ID、source／output mapping、finalize時digestを含むcompact manifestはRestore guardのため保持する。

writeとrollbackの順序

write

  1. lock取得後に対象集合、入力digest、output不在、既存HTML digestを再検証する。
  2. 既存HTMLの変更前sourceをbackupへ保存し、journalをpreparedにする。
  3. 生成HTMLを既存atomicCreateで作る。既存entryはraceを含め上書きしない。
  4. 既存HTMLのlink変更をsnapshot確認後にatomicReplaceする。
  5. Markdownを既存setDocumentArchivedで移す。
  6. active Markdown 0件、生成HTML件数一致、実project diagnostic差分を確認する。
  7. journalをcommittedにし、共有manifest判定がmigration管理下sourceをRestore不可と分類することを確認してからlockを解放する。起動中Viewerへの接続は要求しない。

automatic rollbackと明示rollback

  1. 全対象を先にpreflightし、after digestと一致しない利用者変更が1件でもあれば何も戻さない。
  2. Archive済みMarkdownをactive pathへ戻す。
  3. 変更した既存HTMLをbackupからatomic replaceする。
  4. 生成HTMLがjournal digestと一致する場合だけ削除する。symlinkや変更済みfileは削除しない。
  5. 元のdocument集合とdigestを確認し、journalをrolled-backにする。

crash後にapplyingのjournalが見つかった場合、新しいwriteは開始しない。compact reportでmigration IDと--rollbackを提示する。初期releaseでは自動resumeよりrollbackして再実行する単純な回復経路を優先する。

実装phaseとgate

  1. Phase A — converter completeness（完了）: HTML5 ID、空slug fallback、CSS alignment、tableの見出し由来captionを完成させる。単一文書の代表変換でconverter起因error 0件をgateとする。
  2. Phase B — pure migration planner（完了）: discovery、mapping、Markdown／HTML link rewrite、overlay lint、diagnosticsを副作用なしで実装する。--checkがfilesystemを一切変えないことをgateとする。
  3. Phase C — journaled writer（完了）: lock、backup、create、replace、Archive、automatic rollbackを実装する。任意operationでfailure injectionして元状態へ戻ることをgateとする。
  4. Phase D — recovery（完了）: crash状態の照合、明示rollback、finalizeを実装する。変更済みoutputを上書き・削除しないことをgateとする。
  5. Phase E — product integration（外部gate待ち）: CLI、英日文書、browser、packed consumer、Windowsを揃える。full checkと実dataset acceptanceをrelease gateとする。

Phase AからDと、Phase Eのrepository内作業は同一working treeで完了した。公開versionではcommit履歴を整理し、実datasetとWindows CIのgateを満たしてから一括移行対応としてreleaseする。
