MarkdownからHTMLへの移行リスク再評価（2026-08-19）

結論: 再現済みP0〜P2は実装で対処し、migrate --writeのcode-level見送り条件を解除する

追加監査で再現したArchive destinationのsymlink／既存copy、case／Unicode違いのMarkdown link、retire前filesystemへの誤fallbackを修正した。lossy policy、構造parity、拡張構文診断、caption scope、既存HTML参照、最終再走査、文書別言語、filesystem preflightも追加した。外部評価対象17件と3 OSのrelease gateは、対象datasetとCI環境で別途実行する。

評価範囲と方法

Markdown compiler、migration planner、link rewrite、virtual project lint、Archive、journal、rollback、ViewerのArchive配信をcode reviewした。repositoryの既存fileは変更せず、OSの一時directoryに作成した最小fixtureで候補障害を再現し、fixtureは検証後に削除した。

  • active／archived sourceの配置とsymlink境界
  • case、Unicode、query、fragmentを含むlocal link解決
  • raw HTML、unsafe URL、Markdown拡張構文のlossy変換
  • content parityのfalse positiveとfalse negative
  • table／Mermaid caption、文書言語、既存HTML参照
  • 途中停止、automatic rollback、再実行、cross-platform CI

P1 lossy変換が既定でready=true raw HTMLはliteral textになり、unsafe URLは除去されるが、どちらもwarningである。既定のwriteはwarningを許可し、parityもsanitized後の表現を正解として扱う。repository fixtureでもraw HTMLとunsafe linkを含みながらready=trueを確認した。 source変換noticeを既定blockerにし、明示的な--allow-lossyだけで許可する。既存HTMLのbaseline warningとはpolicyを分離する。
P1 linked imageをparity不一致と誤判定する [![Badge](badge.svg)](other.md)は正しくHTML化されるが、Markdown側はlink labelをBadge、HTML側はanchorのtextContentを空として比較し、MIG004で停止した。tableやheading内の画像にも同型の誤判定があり得る。 HTML側のaccessible textへdescendant画像のaltを含める。link、heading、table cellごとのfixtureを追加する。
P1 parityが文書構造の一部を比較しない visible text、見出し、code、Mermaid、task、画像、link、table値は比較するが、paragraph境界、blockquote、ordered／unordered listと開始番号、nest、強調、取消線、code言語、link／画像title、改行、horizontal ruleは比較対象外である。構造が変わっても一致と判定し得る。 構造factを追加し、compiler tokenごとのsemantic回帰testと役割を分ける。
P1 拡張Markdown構文の扱いが不統一 front matterは既知の非対応であり、見出しとして誤parseされる。footnote、custom heading ID、wiki link、Obsidian embed、MDX、admonition、mathにも専用contractがない。lintで止まる構文と、plain text化して静かに通る構文が混在する。 preflight feature scannerと対応matrixを用意し、非対応構文を固有codeでblockまたは明示noticeにする。footnoteとcustom IDはlocal fragment互換性を含めて対応方針を決める。
P1 caption推論が構造scopeを見ない blockquote内の見出しを、その後のblockquote外tableのcaptionとして採用することを確認した。複数tableでは同じcaptionを反復する。Mermaidはfigure／figcaptionへ変換されず、strictなwarning運用と両立しない。 同じblock scopeにある直前見出しだけを候補にする。曖昧な場合は推測せずblockし、table／Mermaid用の明示caption記法を用意する。
P1 既存HTMLの参照検出範囲が限定的 a[href]とarea[href]だけをrewriteし、既知の画像・script系URL属性はblockする。一方、form[action]、button[formaction]、srcset、meta refresh、CSS、inline script、独自data-*は検出しない。download付きanchorも通常navigationとしてHTMLへ書き換わる。 標準URL属性を網羅し、download／type付きanchorは自動rewriteせずblockする。scriptやdata属性は非対応範囲をreportへ明示する。
P1 mutation中に追加されたdocumentを最終確認しない spec-html同士の操作はlockされるが、editorや別processが追加したMarkdown／HTMLは対象集合へ入らない。最終verificationは管理fileのdigestだけを確認するため、active Markdown 0件と未処理link 0件を実filesystemで再確認していない。 commit直前にdocument集合を再探索し、post-state lintとactive Markdown 0件を確認する。
P2 content root全体へ単一言語を適用する --langは全生成articleへ同じ値を設定する。front matterと文書単位language metadataは非対応なので、mixed-language directoryではアクセシビリティmetadataが誤る。 移行manifestでpathごとの言語を指定できるようにするか、初期releaseでは単一言語rootだけを明示的な前提にする。
P2 filesystem能力と規模のpreflightがない atomic createはhard linkへ依存し、backup pathは元pathより長くなる。network filesystem、Windows path length、非常に大きい文書集合では、check成功後のwriteだけが失敗または高memoryになる可能性がある。 同一filesystem内の能力probe、path長検査、件数／byte数report、規模上限またはstreaming方針を追加する。

今回の監査でも維持できた点

  • invalid UTF-8、input／output symlink、既存HTML targetの上書きを拒否する。
  • 同じdirectoryへHTMLを作るため、通常の相対asset位置は変わらない。
  • exact-caseのMarkdown document linkはqueryとfragmentを保持してHTMLへ書き換える。
  • 生成HTML全件と既存HTMLの差分をvirtual projectとしてLintする。
  • 通常のcreate、replace、Archive、journal更新失敗はautomatic rollback testを通過している。
  • 適用後に編集されたHTMLをrollbackで上書きせず、finalizeで現在値を保持する。
  • Archive sourceはstableなlogical URLで配信するため、通常assetは元directory基準で解決される。

write解禁の受入gate

  1. root直下とnested directoryの.archived symlink、通常file、同名copyを--checkでerrorにし、fileを1件も変更しない。
  2. 上記状態で--writeを直接実行してもmutation前に停止する。
  3. case違いとUnicode正規化違いのlinkをmacOS、Windows、Linuxでcanonical HTMLへrewriteするかblockする。
  4. post-state lintがretire対象Markdownを解決候補にせず、write後のlocal reference errorを0件にする。
  5. linked image、heading内画像、table内画像がfalse parity errorにならない。
  6. raw HTMLとunsafe URLは明示許可なしのwriteをblockする。
  7. front matter、footnote、custom ID、wiki link、MDXを固有診断で分類し、silent degradationをなくす。
  8. commit直前の再探索でactive Markdown 0件と実filesystemのpost-state lintを確認する。
  9. 外部評価対象17件と既存Archive 20件で、check error 0、write成功17、parity 17、active Markdown 0、reference error 0、Archive 37件、rollback後digest一致を確認する。
  10. full checkとpacked migrationをUbuntu、macOS、Windowsで成功させる。

残るrelease検証順序

  1. 外部評価対象17件と既存Archive 20件を取得し、受入gateのdigestまで記録する。
  2. Ubuntu、macOS、Windowsのpacked migration testをCIで通す。
  3. release gate成功後に0.2.0候補としてversioningする。
