Spec HTML 多角プロジェクト評価（0.1.6 / 2026-08-21）

commit 85b4a73のSpec HTML 0.1.6を、製品価値、scope、設計、実装、security、data安全性、test、UX、accessibility、性能、文書、互換性、release、持続性の14観点で評価した。

総合評価: 85 / 100。trusted local用途では採用推奨

0.1系かつ作成から約3日のprojectとしては、書込安全性、回帰test、runtime互換性、利用者向け文書が非常に強い。Markdownのpreview、単体変換、一括migration、HTMLのlint／fix／format、Viewer内編集を、既存sourceを壊さない方向で一貫させている。

一方、公開OSSとしてのtraceabilityと持続性は実装品質に追いついていない。公開済み6 versionにremote git tagとGitHub Releaseがなく、0.1.6はlocal HEADだけでCI未実行である。主要orchestratorの再肥大化、CLI messageの英日混在、固定test port、accessibilityの自動監査不足も残る。

評価範囲と方法

評価対象はlocal mainのcommit 85b4a73で、versionは0.1.6、比較対象のorigin/mainはcommit 616ce0aの0.1.5である。調査開始時点のworking treeはcleanだった。調査途中に出現した本評価と無関係なlocal変更は対象外とし、編集していない。

source、test、英日README、authoring guide、security／release／contribution文書、package metadata、CI設定、公開repository metadata、npm registryを確認した。第三者への利用者調査、screen reader実機試験、penetration test、長期負荷試験は実施していない。

評点の算出方法

各観点を10点満点で採点し、総合点へのweightを合計100にした。総合点は「評点×weight÷10」の合計を四捨五入した85点である。実装の信頼性を重く、project作成直後であること自体を過剰に罰しないようcommunityのweightは2に抑えた。14観点を同じ重さで平均すると8.2 / 10である。

特に強い点

  1. 破壊的操作の設計が慎重である。 変換はcreate-only、一括移行はpreflight、lock、journal、digest、rollbackを備え、Viewer編集もrevision付きatomic replaceを使う。機能ごとの安全策がREADMEの約束と一致している。
  2. test pyramidが実用的である。 pure unitだけでなくHTTP、3 browser、pack後consumer、複数runtime／OS、性能、repository自身の文書まで検査対象にする。0.1系でこの幅は稀である。
  3. Markdownを敵にしない。 Markdownをそのまま読め、必要な文書だけ変換でき、root全体の移行もrollbackできる。採用時に既存資産を一括置換させない。
  4. security modelが正直である。 「localだから安全」と曖昧にせず、trusted HTMLはscriptを実行すること、non-loopback利用の制約、sanitizerではないことを明示している。
  5. 自分のtoolを自分で使っている。 specs/を実際の設計・評価・showcaseへ使い、CIでfix／format／lintを強制するため、dogfoodingが継続的な回帰検出になっている。

改善優先順位

P0の機能blockerは確認していない

trusted local用途を直ちに止める欠陥は見つからなかった。以下は公開前に整えるP1と、次のiterationで扱うP2である。

  1. P1: release traceabilityを実態に合わせる。 少なくとも今後のversionはreview済みcommitへ署名付きannotated tagを付け、GitHub Releaseを作る。可能なら既存0.1.0〜0.1.5もnpm publish時刻とcommitを照合して補完する。release gateへtag／Release存在の事後確認を追加し、npm provenanceも検討する。
  2. P1: 0.1.6をremote CIで通してから公開する。 localの全stageは成功したが、commit 85b4a73はorigin/mainより1 commit先である。6 jobsの成功とnpm未公開を再確認してからpublishする。
  3. P1: user-facing messageを英語既定へ統一する。 format、fix、convert、migrate、Host設定、safe writeのerrorをtyped errorまたはmessage catalogへ寄せる。成功条件はCLI testで日本語literalの混入を検知し、READMEの言語方針と実出力が一致すること。
  4. P1: orchestration hotspotを責務境界で縮める。 行数だけを目的に分割せず、browser/start.tsのsource editor／outline／routing lifecycle、cli/options.tsのcommand別parser、server/routes.tsのstate mutation route、migrate/planner.tsのpreflight群を独立APIへ寄せる。fan-outと変更影響範囲を測る。
  5. P2: Playwright serverのport衝突をなくす。 test専用の空きport選択を自動化し、別のSpec HTML Viewerが4173で動いていてもnpm run checkが成功するintegration testを追加する。
  6. P2: accessibilityの外部基準を導入する。 axe等の自動検査を主要画面状態へ追加し、keyboard-only、screen reader、high contrast、reduced motionの手動checklistをrelease文書へ入れる。
  7. P2: 大規模性能を継続監視する。 5,000文書を毎回CIへ入れる必要はないが、scheduledまたはrelease gateで予算を持つ。検索は現時点で必須ではなく、実利用でnavigation到達性が問題化した時点で導入する。
  8. P2: supply-chain hardeningを追加する。 GitHub Actionsをcommit SHAへpinし、Dependabotで更新する。公開tarballのprovenance、checksum、SBOMの費用対効果もrelease運用と合わせて決める。

過去評価からの変化

0.1.2の11観点評価で弱点だったMarkdown lint、非loopback mutation保護、CLI help、security policy、repository metadata、navigation cache、runtime層分離、browser controller test、benchmarkは改善済みである。詳細は0.1.3準備の対処記録に残っている。

新たな課題は、0.1.5／0.1.6で追加したdocument action、outline、source editorによるbrowser orchestrationの再肥大化と、公開version数が増えてもtag／Releaseが作られていない点である。つまり、品質は全体として上がったが、実装surfaceとrelease負債も同時に増えた。
