Markdown閲覧・HTML変換 実装計画

決定: 直接閲覧と永続変換を同じrelease scopeで実装する

既存projectでは設計書と実装計画書がMarkdownで作られ続けている。Markdownを読めないViewerと、Markdownから移行できないHTML workflowのどちらか一方だけでは、既存資産との併存期間に導入障壁が残る。そのため、既存Markdownを無変更で閲覧する経路と、選択した文書を編集可能なSpec HTMLへ変換する経路を、1つの共有renderer上に実装する。

実装状況: 実装・code review反映済み

直接閲覧、共有compiler、archive、cross-format navigation、source表示、create-only conversion、package consumer testまで実装した。reviewではBOM、空h1、文字参照、画像alt、絶対URL検証、archive内hidden file、programmatic language検証、変換result改変、Markdown Mermaid callbackを追加でhardeningした。

本計画はMarkdown閲覧対応案の評価を実装可能な単位へ落とし込んだものである。評価時点では段階的な採用としていたが、既存Markdown資産との衝突が導入判断を左右するため、両機能の提供をrelease条件へ変更する。

目的と完了条件

  1. 既存の.mdと.markdownを移動、複製、事前buildせず、HTML文書と同じViewerで読める。
  2. MarkdownとHTMLのrelative link、heading fragment、history、theme、print、archive、live reloadが一貫して動く。
  3. 明示的なCLI操作でMarkdownから1つのroot article[lang]を持つSpec HTML draftを生成できる。
  4. 閲覧と変換が同じMarkdown parser、heading ID、URL policy、Mermaid変換を使う。
  5. 既存HTMLの表示、lint、fix、format、archive、security testを回帰させない。
  6. Markdownと変換後HTMLが併存しても、暗黙に片方を隠さず、利用者が形式を識別して比較できる。

固定する設計判断

実装開始前に固定する主要判断
論点 決定 理由
機能scope Markdown previewとMarkdown→HTML conversionを同時に提供 片方だけでは既存資産と新規HTML workflowの間に手作業が残る。
document identity content rootからの相対pathを拡張子込みでidentityにする design.mdとdesign.htmlを独立して参照、archiveできる。
同名文書 両方表示し、Markdownへ常にMD badgeを付ける 古いHTMLが新しいMarkdownを隠すstale-content問題を避ける。
変換後の所有権 生成したHTMLを独立したsource of truthにする HTMLへの手編集をMarkdown再変換で失わない。
Parser markedとgithub-sluggerを直接利用 GFM主要機能、Node.js／browser共用、GitHub互換heading IDを小さい構成で得られる。
Raw HTML Markdownでは実行せずliteral textとして扱う 一般的なREADMEを新たなscript実行対象にしない。
Markdownの言語 Viewerは--markdown-lang、converterは--langで指定 自動言語判定を避けつつ、article[lang]を生成する。
永続変換 標準出力またはcreate-onlyの明示的な--output 既存fileを上書きせず、pipeと安全なfile生成の両方を提供する。
HTML command fixとformatはHTMLだけを対象に維持 MarkdownをHTML formatterへ誤投入せず、sourceを勝手に書き換えない。

Document modelとpath contract

type DocumentFormat = "html" | "markdown";

interface ContentDocument {
  absolutePath: string;
  path: string; // content-root relative POSIX path, extension included
  format: DocumentFormat;
}
  • 対応拡張子はcase-insensitiveな.html、.md、.markdown。
  • .htmは現在の探索対象でないため、今回もdocumentとして追加しない。
  • absolute path、backslash、NUL、空segment、.、..は従来どおり拒否する。
  • dot directory、node_modules、symbolic linkは従来どおり探索しない。
  • nav.htmlの既存除外は維持し、nav.mdは通常のMarkdown文書として扱う。
  • archive conflictは拡張子込みの同一pathだけを対象とする。

探索APIの分離

現在のfindContentDocumentsを無条件にMarkdown対応へ変えると、lint、fix、formatがMarkdownをHTMLとして処理する。これを避けるため、内部の再帰探索を共有し、利用目的を明示するwrapperを設ける。 

findViewerDocuments(root) // HTML + Markdown
findHtmlDocuments(root)   // HTML only
documentFormatFromPath(path)
normalizeViewerDocumentPath(path)
  • navigation、archive、document stateはfindViewerDocumentsを使う。
  • lint、fix、formatの既存HTML処理はfindHtmlDocumentsを使う。
  • routerとserverは同じnormalizeViewerDocumentPathを使う。
  • asset配信のpath検証とviewer documentの拡張子検証を混同しない。

共有Markdown compiler contract

interface MarkdownCompileOptions {
  language: string;
}

interface MarkdownCompileResult {
  fragment: string; // one article[lang] root
  title: string | null;
  headings: readonly { depth: number; id: string; text: string }[];
  notices: readonly MarkdownNotice[];
}

compileMarkdownは同期的で副作用のないpure functionとし、browser、navigation、converterのどこから呼んでも同じ入力とoptionから同じ結果を返す。globalなmarked.useを使わず、設定済みinstanceをmodule内で1回だけ構築し、test間のextension重複を防ぐ。

記法 出力 補足

URL policy

  • linkはrelative URL、fragment、http、https、mailto、telを許可する。
  • imageはrelative URL、http、httpsを許可する。
  • javascript、vbscript、file、dataと不正URLは属性へ出力しない。
  • 拒否したlinkはlabelだけ、imageはalt textだけを残し、noticeを返す。
  • URL policyはrendererで適用し、click handlerだけへ依存しない。

言語指定

  • Viewerへ--markdown-lang <language-tag>を追加し、既定値は現在のframeと同じenにする。
  • converterの--langは必須とする。
  • 両optionは同じBCP 47 validatorを使い、可能ならcanonical formへ揃える。
  • HTML文書内の既存article[lang]は変更しない。
  • 文書単位のfront matter対応は別issueとし、root単位のdefaultだけを初期実装する。

Viewerの挙動

Navigation

  • HTMLは現在と同じh1抽出、Markdownはcompilerの最初のh1をtitleにする。
  • h1がなければ、すべての形式で拡張子を除いたfile名をfallback titleにする。
  • index、overview、readmeの優先順位は拡張子に依存させない。
  • Markdown項目には常に可視のMD badgeとaccessible nameを付ける。
  • 同じstemのHTMLとMarkdownは両方表示し、同順位ではpath順でHTMLを先にする。

Document load

  1. routeから拡張子込みのdocument identityとformatを解決する。
  2. 既存/_content/ routeから元sourceを取得する。
  3. HTMLはpass-throughし、Markdownだけをshared compilerへ渡す。
  4. 得られたfragmentを既存buildSrcdocへ渡す。
  5. 元sourceとformatを保持し、source dialogのlabelを更新する。
  6. frame link handlerを設置し、.html、.md、.markdownをViewer内遷移させる。

Markdownのrelative image URLは、現在と同じbaseへ元の/_content/path/to/file.mdを設定することで解決する。変換後fragmentの仮想URLを新設しない。

Markdown→HTML conversion CLI

spec-html convert <input.md> --lang <language-tag>
spec-html convert <input.md> --lang <language-tag> --output <output.html>
spec-html convert --help

Option contract

convert commandの引数
項目 要件
input 1つの通常UTF-8 file。.mdまたは.markdown。symbolic linkは拒否。
--lang 必須のBCP 47 language tag。
--output 任意。入力と同じdirectoryにある新規.html pathだけを許可。省略時はHTMLだけをstdoutへ出す。
既定出力名 暗黙には作らない。file生成には明示的な--outputを必要とする。

directory入力、glob、複数output、--force、--watchは受け付けない。directory名convertをViewerで開く場合は、既存subcommandと同様に./convertと指定する。

Conversion pipeline

出力とdiagnostics

  • stdout modeではstdoutにHTML以外を混ぜず、noticeとlint diagnosticをstderrへ出す。
  • file modeでは作成pathとdiagnostic summaryをstdoutへ出す。
  • 構文的に正しいdraftは、semantic lint errorが残っていても明示的なfile modeなら作成する。
  • lint errorが残る場合はexit code 1、usageまたはI/O failureはexit code 2とする。
  • Markdown tableのcaptionなど、sourceにない意味を捏造してexit code 0にしない。
  • project全体のrelative reference検査は、作成後のspec-html checkへ委ねる。

Safe create

既存atomicReplaceは存在する通常fileのmodeを維持して置換するため、create-onlyへ流用しない。safe-write.tsへ新しいatomicCreateを追加する。

  1. 出力directoryをrealpathで解決し、入力directoryと一致することを確認する。
  2. 出力targetが存在しないことを確認する。symbolic linkを含め、存在するentryはすべて拒否する。
  3. 同じdirectoryへ排他的な一時fileを作り、UTF-8出力を書いてsyncする。
  4. 既存targetを置換できないno-clobber operationで公開する。
  5. raceでtargetが作られた場合は失敗し、相手のfileを変更しない。
  6. 成功・失敗のどちらでも一時fileを残さない。

Lint、fix、format、checkとの境界

mixed content rootに対するcommand別の対象
Command HTML Markdown
Viewer 表示 compileして表示
lint 既存ruleで検査 初期releaseでは対象外と明記
fix 既存処理 対象外、変更しない
format 既存処理 対象外、変更しない

Markdownを黙ってHTML linterへ渡さないことを優先する。READMEとhelpへ対象範囲を明記し、mixed directoryでcheckが成功してもMarkdown自体を検査した意味ではないことを説明する。Markdown source位置に対応したlintは後続機能として別設計する。

既存projectへの導入workflow

  1. 既存のMarkdown directoryをそのままspec-htmlで開き、navigation、relative link、画像、Mermaidの互換性を確認する。
  2. Markdownをsource of truthのまま使う文書は変換しない。

自動整理しない理由

元Markdownが別toolやagent workflowのsourceである可能性がある。converterはその関係を判断できないため、削除、rename、archiveを自動化しない。

Raw HTML実行 trust boundary拡大 rendererでliteral text化し、unsafe URLも生成時に拒否する。
同名文書のstale HTML 新しいMarkdownが見えない 両方を表示し、Markdownへ常時MD badgeを付ける。
Conversion overwrite 手編集済みHTMLの消失 create-only、snapshot、no-clobber publish、上書きoptionなし。
Semantic情報不足 生成HTMLにlint errorが残る draft contractとdiagnosticsを明示し、意味を自動推測しない。
Browser bundle増加 初回loadと配布size増加 parserを1つに限定し、build前後のsizeをrelease gateで確認する。
Parser upgradeでHTML差分 heading URLや生成diffの変化 exact version、lockfile、golden test、明示的なupgrade review。

実装後reviewで追加したhardening

  • 先頭UTF-8 BOMをcompiler境界で除去し、Viewer、navigation、conversionを一致させた。
  • 空の最初のh1はtitleなしとしてfile名へfallbackし、文字参照と画像altには描画後のtext semanticsを使う。
  • URLの文字参照を検査前に正規化し、許可schemeを確認した後もmalformed percent encodingを拒否する。
  • archive directoryへ直接置かれたdot-prefixed fileを探索対象から除外する。
  • CLI以外のserver起動でもMarkdown language tagをcanonicalize、validationする。
  • conversion resultの検証済みoutput pathと生成内容をsnapshotへ固定し、返却object改変による未検証書込を拒否する。
  • Markdown由来のMermaidを識別し、既存HTMLはloose、Markdownはstrictで描画する。

Release gate

  • Markdown previewとconvertの片方だけを有効にした状態でreleaseしない。
  • HTML-only fixtureの既存testを削除または弱めて通さない。
  • raw HTML、unsafe URL、Markdown Mermaid callbackのnegative browser testがない状態でreleaseしない。
  • create-only raceとpartial file cleanupのfailure testがない状態でreleaseしない。
  • packed consumer環境で両機能を確認するまで完了扱いにしない。
  • README英日版、authoring guide英日版、help、CHANGELOGが同期するまで完了扱いにしない。

Rollback方針

Viewer対応はdisk上の既存documentを変更しないため、問題があればMarkdownをdocument探索から外すことで旧挙動へ戻せる。converterはcreate-onlyなので、rollback時も元Markdownと既存HTMLを変更しない。すでに利用者が作成したHTMLは利用者所有のfileとして残し、自動削除しない。
