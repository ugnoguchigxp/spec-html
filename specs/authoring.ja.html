Authoring guide

これは、Spec HTMLの文書を生成・編集するLLM向けの最小ルールです。本文は標準のsemantic HTMLで直接書き、細かな誤りはLinterの診断に従って直します。

ルール

  1. 各fileは、主言語を示すlang属性を持つ1つのarticleをrootにしたHTML fragmentにする。html、head、bodyは書かない。
  2. 文書の題名としてh1を1つ置き、内容に合う標準HTML要素を選ぶ。独自要素や独自componentは作らない。
  3. 要件、結論、数値などの重要な情報はHTML本文に書く。scriptやcanvasなどは、本文を補強するためだけに使う。
  4. 文書間linkとassetは、content directory内のfileを指す相対URLで書く。

既存Markdownを扱う

Viewerは.mdと.markdownも探索します。見出し、段落、強調、listとtask list、blockquote、code、GFM table、link、画像、mermaid fenceを表示し、相対URLはMarkdown fileの位置から解決します。raw HTMLはliteral textとして表示し、危険なURL schemeを除去し、Mermaidのstrict security levelでcallback directiveを無効化します。 

spec-html ./specs --markdown-lang ja
spec-html convert ./specs/design.md --lang ja
spec-html convert ./specs/design.md --lang ja --output ./specs/design.html
spec-html migrate ./specs --lang ja --check
spec-html migrate ./specs --lang ja --write
spec-html migrate ./specs --lang ja --language-map ./specs.languages.json --check

--outputを省略するとstdoutへHTMLだけを出力します。明示する場合は、入力と同じdirectoryにある未作成の.htmlを指定し、既存の通常fileやsymbolic linkは上書きしません。変換時に元Markdownを削除、rename、archive、同期することもなく、commandは元Markdownを残したことを明示します。Viewerでは元Markdownと生成HTMLを別文書として表示します。両方を正本にせず、生成後のHTMLは独立した編集対象として扱います。

変換は数字から始まるIDを含むGitHub互換の見出しIDを維持し、GFM tableのcell揃えをdeprecatedなHTML属性なしでViewer CSSへ割り当てます。GFM tableには直前の見出しtextを実際のcaptionとして複製し、前に見出しがないtableはlint errorのままにします。

正本を一括切替する場合はmigrateを使います。check modeはfileを変更しません。write modeは同じdirectoryへHTMLを作成し、対象document linkを書き換え、Lintとcontent parityを検証し、全preflight成功後だけMarkdownをArchiveへ移します。変更していない移行全体はmigration IDで--rollbackできます。HTMLの採用確定後は--finalizeで現在の内容を保持し、rollback backupだけを削除します。migration管理下のMarkdownはArchiveで閲覧できますが、個別Restoreできません。

raw HTMLや危険URL除去のlossy変換は、--allow-lossyを明示しなければblockします。front matter、footnote、custom heading ID、wiki link、GitHub alert、数式拡張にはsource位置付きの非対応診断を返します。tableとMermaid diagramは同じblock scope内の先行見出しだけをcaptionに使います。複数言語のrootではJSON language mapでexact Markdown pathごとにfallbackの--langを上書きできます。

preflightは既存Archive copyと安全でないArchive directoryを拒否し、容量とportable path長を確認し、form、download、media属性、CSS、script、data属性に残る非navigation Markdown参照を報告します。write modeはcommit直前にも全documentとlinkを再走査し、active Markdownが残れば移行全体をrollbackします。

lint、fix、format、checkが処理するのはHTMLだけです。mixed directoryのcheck成功はMarkdown sourceの検査を意味しません。正本切替前にmigrate --checkでMarkdownからHTMLへのplan全体を検証してください。

HTMLのTypoを修正する

tag名、attribute名、引用符、閉じtag、閉集合のattribute値、ID、local pathの明白な誤りにはFixerを使います。FixerはHTML表層だけを変更し、文章、script本文、event handler属性値のJavaScriptは書き換えません。 

spec-html fix ./specs --check
spec-html fix ./specs --write

Formatterで整える

作成後のHTMLはFormatterでインデントと改行を統一します。--checkは変更せずに差分の有無を確認し、--writeは変更fileだけを書き換えます。 

spec-html format ./specs --check
spec-html format ./specs --write

full HTML documentも入力できます。安全なdocument wrapperとmetadataはfragmentへ正規化されますが、headにstyle、script、link、baseがある場合やwrapperに表示・動作へ影響する属性がある場合は変換されません。Formatterはalt、caption、見出し、semantic elementなど、内容の意味を選ぶ修正を行いません。

Lintで確認する

詳細な禁止事項や要素ごとの規約を覚える必要はありません。作成・編集の後にLinterを実行し、errorを修正します。warningも必要に応じて改善し、CIではerrorとして扱えます。 

spec-html lint ./specs
spec-html lint ./specs --warnings-as-errors

診断の修正方法が分からない場合だけ、rule IDを指定して確認します。

spec-html lint --explain DOC001

全ての検査を一括実行する

checkはFixer、Formatter、Linterの順で一括実行します。既定ではfileを変更せずに全ステージの結果を報告します。--fixを付けると、安全なFixerとFormatterの変更を適用してから結果をLintします。 

spec-html check ./specs
spec-html check ./specs --fix

必要な組み合わせだけを実行する場合は処理を選択します。例えばFixerとLinterは--fixer --lint、FixerとFormatterは--fixer --formatを指定します。

最小テンプレート

<article lang="ja">
  <h1>文書の題名</h1>

  <section id="overview">
    <h2>概要</h2>
    <p>文書の要点です。</p>
  </section>
</article>

Chart.jsの例

Chart.jsを使う場合は、canvasをfigureに入れてaccessible nameを付け、inline scriptからglobal Chart APIを呼び出します。JavaScriptが動かない場合にも内容を確認できるよう、正確な値は通常のHTMLにも残します。 

<figure>
  <canvas id="latency-chart" aria-label="versionごとのP95 latency"></canvas>
  <figcaption>P95 latency: 2.1 = 180 ms、2.2 = 220 ms、2.3 = 230 ms</figcaption>
</figure>

<script>
  new Chart(document.getElementById("latency-chart"), {
    type: "line",
    data: {
      labels: ["2.1", "2.2", "2.3"],
      datasets: [{ label: "P95 (ms)", data: [180, 220, 230] }]
    }
  });
</script>

Mermaidの例

Mermaidを使う場合だけ、図のsourceをpre.mermaidへ書き、figureとfigcaptionで説明を付けます。 

<figure>
  <pre class="mermaid">
flowchart LR
  Browser --> API
  API --> Database
  </pre>
  <figcaption>Request flow</figcaption>
</figure>
