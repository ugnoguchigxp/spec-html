Markdown migration parity補正 実装計画

採用方針: 比較条件を緩めず、fact抽出とformatterを正して厳密parityを維持する

vulnWorkbench 17文書で再現した13件のMIG004は、DOM取得順、inline text連結、inline code整形に起因する。Markdown本文を変更したり、配列をsortして構造順を捨てたり、code内空白を一律normalizeしたりせず、生成HTMLがMarkdownの意味とverbatim dataを保持するようspec-html側を修正する。

受入条件は、同じread-only preflightでcontent parityが4/17から17/17へ改善し、意図的な見出し順変更、list種別変更、table文字列変更、inline code変更は引き続き不一致になることである。

維持するcontent parity contract

修正後も、parityは「同じ要素が存在すればよい」というbag比較にはしない。文書の意味を構成する順序、種類、値を保持する。

factごとの比較契約
fact 保持するもの 許容する差
headings document order、level、ID、visible text HTML sourceのindentだけ
lists document order、ordered／unordered、start、nest depth、direct item数 HTML sourceのindentだけ
inline marks document order、strong／em／delの種類 HTML sourceのindentだけ
heading／link／table cell text inline tokenと画像altの位置、意図された空白、句読点との隣接 連続するHTML layout whitespaceの表示上の正規化
inline code Markdown lexerが確定したcode textの全文 なし。formatterが変更しない。

inline codeは「画面では同じに見える」ことを理由に空白normalizeしない。command、path、placeholderはcopy、search、後続編集でverbatim dataとして使われるため、formatter側で保持する。

実装設計

1. heterogeneous要素をDOM順で収集する

querySelectorAll("h1, …")のような複合selectorへ順序を依存させない。article以下をpre-orderで一度走査し、HtmlElementの配列を作る。同じ配列をheadings、lists、marksのfilter元にする。

実装形の擬似code 
function descendantElementsInDocumentOrder(root: HtmlElement): HtmlElement[] {
  const result: HtmlElement[] = [];
  const visit = (parent: HtmlElement): void => {
    for (const child of parent.childElements) {
      result.push(child);
      visit(child);
    }
  };
  visit(root);
  return result;
}
  • headingsはh1〜h6だけをfilterする。
  • listsはolまたはulをfilterする。
  • marksはstrong、em、delをfilterする。
  • 配列をtag名でsortしない。nested elementは親より後、後続siblingより前になる。
  • 単一selectorで現在問題のないtable、row、image等は不要に書き換えない。

2. accessible inline textを位置どおり連結する

accessibleHtmlTextはtext nodeをそのまま追加し、画像ではその位置にaltを追加する。最後はjoin("")とし、node境界を理由にseparatorを入れない。既存call siteのnormalizeVisibleTextが実在するHTML whitespaceだけを1個へ正規化する。

  • A<code>B</code>CはABC。
  • A <code>B</code> CはA B C。
  • A<img alt="B">CはABC。
  • 日本語の助詞・読点・括弧の前後へ英語向けseparatorを追加しない。

broad smoke checkであるvisibleHtmlTextは今回変更しない。役割の異なる正規化まで同時に変えると、既存15 factのどれが回帰したか分かりにくくなるためである。

3. inline code本文をformatterから保護する

formatHtmlが既にpre、textarea、script、styleへ使うmarker方式を、standalone codeのcontentにも適用する。Prettierへは短い一意markerだけを渡し、format後に元source sliceを完全復元する。

  • codeが別の保護対象codeまたはraw elementのdescendantなら、outer要素だけを保護してoverlapを避ける。
  • 保護候補のうち保護対象ancestorを持たない最外要素だけを採用し、source offsetの降順でmaskする。
  • 複数inline code、entity、連続空白、100文字超、既存marker prefixをtestする。
  • markerが0件または複数件になった場合は、現在と同様にformatter errorとして停止する。
  • 復元後のformatter idempotenceを確認する。

全inline codeに属性を付ける案、PrettierのhtmlWhitespaceSensitivityを変更する案、parity側で空白をcollapseする案は採用しない。実測ではcss、strict、ignoreのいずれも長いcode本文を保持せず、global option変更は通常HTMLのlayoutへ波及する。

4. 厳密比較と診断codeを維持する

compareFactとMIG004の外部contractは変更しない。今回の修正はexpected／actualを同じ意味表現へ揃えるもので、比較器を寛容にするものではない。messageへ文書本文を含む詳細diffを出す変更も、このpatchには含めない。機密文字列のlog出力とreport schema変更を避ける。

rollback方針

source変更は2つの独立commitへ分ける。回帰時はmigration safety機構を変更せず、該当commitをrevertする。parity修正の途中versionをreleaseせず、17/17とnegative testの両方を満たさなければ現行ready=falseの安全側挙動を維持する。

  • WP1 rollback: DOM順helperとtext連結だけを戻す。
  • WP2 rollback: inline codeのmarker保護だけを戻す。
  • vulnWorkbench側はread-only canaryだけなのでrollback対象の変更を作らない。
  • release後に回帰が見つかった場合はmigrate --writeの推奨を止め、patch releaseで修正する。

Definition of Done

  1. RC1〜RC4を再現するfocused testが修正前に失敗し、修正後に成功する。
  2. headings、lists、marksの意図的な順序・種類・値変更がparity不一致になる。
  3. table／heading／link内のinline要素隣接でsourceにない空白を生成しない。
  4. 100文字を超えるinline code、entity、連続空白がformat前後で完全一致する。
  5. pre > codeを含む既存raw content保護とformatter idempotenceが回帰しない。
  6. 既存migration lifecycle、rollback、link、security testがすべて成功する。
  7. npm run checkが3 OS相当のCI matrixで成功する。
  8. vulnWorkbenchのread-only preflightがparity=17/17、errors=0、ready=trueになる。
  9. vulnWorkbenchのMarkdown本文、file配置、digest、git statusが変更されていない。
  10. language mapとArchive判断を完了するまで、外部canaryの成功をwrite承認として扱わない。

localのtypecheck、対象fileのlint、coverage 429 tests、build、browser 33 tests、pack、現行specs/ 13件の--warnings-as-errors checkは成功した。repository全体のnpm run checkは、この変更と別に進行中のbrowser module分割とplanner変更に残る未使用import 3件でlintが停止する。また、docs/からspecs/への移動に対してdocs:checkは旧pathを参照している。いずれもparity実装のfailureではないが、release完了条件としては並行変更の統合後にfull checkを再実行する。
