強み

  1. 書込安全性が製品水準である。 digest snapshot照合、temp fileからのatomic replace、hard linkによるcreate-only公開、symbolic link拒否を全書込経路で共有する。migrateはさらにcross-process lock、journal状態機械、失敗時rollbackを備える。
  2. filesystem境界の防御が一貫している。 HTTP pathをsegment単位で検証し、..、NUL、backslash、dotfileを拒否したうえで realpath後にroot内かを再確認する。content rootを信頼境界と明示し、symlinkを追跡しない。
  3. 検証が実利用に近い。 unitだけでなくHTTP統合、Playwrightによる3 engine、そしてnpm pack 後のconsumer projectでCLI全体をsmokeする。release品質の安全網として機能している。
  4. 型のdisciplineが効いている。 strictに3種の追加厳格化を加え、any、@ts-expect-error、 TODO commentを0件に保っている。型assertionもmarked token、DOM、動的JSONという外部境界に限定されている。
  5. 互換性を宣言ではなくmatrixで担保している。 Node 3 version、Bun、3 OSを常時検証し、Windowsのpin理由はupstream issue番号付きで記録される。
  6. 設計判断が追跡可能である。 非目標、risk、rollback、release gateがSpec HTML文書としてspecs/ に保存され、機能追加の経緯を後から辿れる。

リスクと改善backlog

最も深刻なリスク: 非loopback公開時のPUT

requestOriginMatchesはOriginヘッダが存在しない場合にtrue を返す。既定の127.0.0.1 bindでは実害が小さいが、--host 0.0.0.0 と--allowed-hostを併用してLANへ公開すると、Originを送らないclientが文書のArchive とRestoreを実行できる。Origin必須化、token、または状態変更APIのloopback限定が必要である。

構造上の負債

依存は概ねCLIを起点とした一方向で、循環依存は検出されなかった。唯一の例外がcontent からmigrateへの逆方向依存である。下位層であるcontentがmigrationという上位機能の概念を知っているため、Viewerとserverも content/archive.ts経由でmigration ownershipに間接的に結合する。

もう1つの負債は巨大fileへの集中である。500行超は9 fileあり、内訳はfix/document.tsが1,057行、browser/start.ts が966行、migrate/planner.tsが827行である。migrate/parity.ts のようにdomain固有で凝集が高いものは現状維持で妥当だが、browser/start.ts はUI、fetch、history、archive、live reloadが同居しており、変更riskが最も高い。

coverageの穴も同じ場所に偏る。src/server/integrations.tsはlines 5%、src/convert/diagnostics.tsは50%、src/migrate/diagnostics.ts は55%である。実装の問題ではなく、成功経路中心のtest配分の結果である。

最終判断

0.1.2は前回評価のrelease blockerを両方解消し、「改善が一般利用者へ届いていない」という留保は解除できる。npm latestとHEADが一致し、全CIがgreenで、脆弱性0件、coverage 87.75%という状態は、信頼できるlocal環境で仕様書を読む用途には十分な水準である。公開Web、untrusted HTML、大規模ナレッジの検索基盤としては、このversionの対象外である。

評価軸を細分すると弱点の性質が明確になる。core実装の品質（84%）と、製品としての完成度（64%）に20 pointの差がある。具体的には、npm公開CLIなのにCLI出力が日本語固定で英語READMEと乖離していること、公開済み3 versionにtagとReleaseがなくrelease手順が未完遂であること、Markdownが検査対象外のまま無報告でgreenになること、性能が一度も測定されていないことである。いずれも実装難易度は低く、P0 3件を解消すれば80前後、P1まで進めれば86前後を見込める。

次の判断点は、利用者が増える前に言語方針とrelease traceability を確定させることである。どちらも後から変更するとbreaking changeまたは履歴の欠損になるため、機能追加より先に処理する価値がある。community観点の低評価は作成2日目としては自然であり、総点を押し下げすぎないよう重みは4に抑えている。
