HTML document Formatter 実装計画

本書は、Spec HTMLで扱うHTML fragmentとfull HTML documentを受理し、安全なdocument envelope正規化と決定的なレイアウト整形を行うFormatterの実装計画を定める。実装者は本書の固定事項を選び直さず、taskごとの変更範囲と検証条件に従って実装する。

1. 目標

  • 人間とLLMが生成したHTMLを、同じ入力から常に同じ出力を得られる形式へ整える。
  • HTML fragmentを第一級入力としながら、一般的なfull HTML documentも入力として受理する。
  • full documentのdoctype、html、head、bodyを入力用envelopeとして扱い、保存結果をfragmentへ正規化する。
  • inline whitespace、raw text、comment、inline scriptを壊さず、Viewerでの表示と動作を維持する。
  • 既存Linterを出力検証のsource of truthとして使い、Formatterが新しいlint違反を作らない。
  • Core API、CLI、compact/JSON report、testを分離し、LLMが小さなtask単位で実装できるようにする。

1.1 成功状態

  • spec-html format ./specs --checkが、変更が必要なfileを決定的な順序で報告する。
  • spec-html format ./specs --writeが、変換可能な全fileを同じ規則で整形する。
  • file pathを指定した場合は、そのHTML fileだけを検査または整形できる。
  • fragmentとfull documentのどちらを入力しても、出力はfull document wrapperを持たないfragmentになる。
  • 同じsourceを2回整形しても2回目の出力が変わらない。
  • 既存のdocsとexamplesを整形後もLinter、Viewer、browser testで利用できる。

2.1 Formatter、Normalizer、Fixer、Linterの境界

各componentの責務
Component 行うこと 行わないこと

Formatter 空白、インデント、属性の折返し、quote、改行code、final newlineを正規化する。 element名、属性値、本文内容、node順を意味的に変更しない。

Prettierが担当するprintingとproject固有のenvelope変換を別moduleにする。FormatterからLinterのprivate関数を呼ばず、公開されているlintDocumentと共有型だけを利用する。

3. 入出力契約

3.1 Fragment入力

explicitなtop-level htmlを持たないsourceをfragmentとして扱う。Formatterはfragmentのroot構造を変更せず、レイアウト整形後に既存Linterを実行する。単一articleでないfragmentも構文が解析できれば整形できるが、DOC001などのdiagnosticは結果へ残す。

3.2 Full document入力

explicitなtop-level htmlと、その子孫にexplicitなbodyを持つsourceをfull documentとして扱う。DOCTYPEは任意、headはexplicitでも省略でもよい。bodyだけ、DOCTYPEだけ、複数のtop-level html、またはhtml外の意味のあるtextやelementはunsupported envelopeとして拒否する。

document判定を正規表現だけで行わない。html-validateのpublic Parserとtag eventのsource locationを使い、comment、attribute内文字列、script本文に現れる<html>を誤認しないようにする。body内容はDOMの再serializeではなく、元sourceのbody開始tag末尾から終了tag先頭までをsource offsetでsliceする。

3.3 Canonical output

  • UTF-8 textとして扱い、BOMを出力しない。
  • 改行codeはLFに統一する。
  • file末尾は改行1個にする。
  • full document wrapperを出力しない。
  • HTMLのtag名とattribute名はPrettierのHTML printerが出力するcanonical表現に従う。
  • optional end tagはPrettierの出力に従い、Spec HTML独自処理で削除しない。

4. Full document envelope正規化

Normalizerは次の表だけを実装する。表にないhead contentやwrapper attributeを推測で処理しない。

Full documentからfragmentへの変換規則
対象 条件 処理 結果
DOCTYPE 0個または1個 削除する。 document-envelope-removedを記録する。
html langとdir以外のattributeがなく、存在する許可attributeをroot articleへ安全に移せる wrapperを削除する。 許可attributeは後述の条件でroot articleへ移す。
head attributeがない wrapperと許可metadataを削除する。 削除したtitleとmetaの種別と個数を記録する。
title head直下 削除する。 textをcompact出力へ含めず、JSON changeのdetailだけに最大60文字で保持する。
meta head直下 削除する。 attribute値は出力へ反復せず個数だけを記録する。
head comment HTML Validate directiveではない head source rangeと一緒に削除する。 個別解析や個数の記録は行わない。
base 常に 変換を拒否する。 Viewerが設定するdocument URL基準のbaseと競合するためFMT002を返す。
style、link 常に 変換を拒否する。 表示に必要なstyleを黙って失わないためFMT002を返す。
head script typeを問わない 変換を拒否する。 実行順やdataを失わないためFMT002を返す。
その他のhead element 常に 変換を拒否する。 未定義の変換を行わずFMT002を返す。

root article bodyの意味のあるroot nodeがarticle 1個だけ article自身に値がなければbody、次にhtmlの順でlangとdirをコピーする。 envelope-attribute-copiedを記録する。
article以外のbody内容 構文が有効で、htmlとbodyにattributeがない body inner sourceをそのままfragment候補にする。 wrapperを追加せず、最終LinterのDOC001やDOC002を残す。移せないlangまたはdirがある場合はFMT003で拒否する。

4.1 拒否するwrapper attribute

htmlまたはbodyにclass、id、style、data-*、event handler、ARIA attributeなどがある場合はFMT003で変換を拒否する。articleへの一括移動はCSS selector、script、accessibility treeを変える可能性があるため行わない。headにattributeがある場合も同様に拒否する。

4.2 Commentとtrivia

body内のcommentはsource sliceに含めて保持する。DOCTYPE、html開始前、html終了後、head内のcommentはdocument envelopeの一部として削除するが、comment専用parserや個別changeは作らない。HTML Validate suppression directiveを含むsourceは既存HTML004に従い、Normalizerがdirectiveだけを消して成功扱いにしない。

5. レイアウト整形規則

5.1 Prettier固定設定

const FORMAT_OPTIONS = {
  parser: "html",
  tabWidth: 2,
  useTabs: false,
  printWidth: 100,
  htmlWhitespaceSensitivity: "css",
  embeddedLanguageFormatting: "off",
  endOfLine: "lf",
  singleAttributePerLine: false,
} as const satisfies prettier.Options;

prettier.resolveConfig、prettier.getFileInfo、plugin探索、.prettierignoreは使用しない。HTML parserと上のoptionを直接prettier.formatへ渡す。Prettierのformat APIは非同期なので、Core APIも最初から非同期にする。

5.2 Whitespace safety

  • htmlWhitespaceSensitivity: "css"を使い、標準のinline element前後の空白を保持しながらblock elementを読みやすく整形する。T0 spikeでstrictがblock構造まで1行へ連結することを確認したため採用しない。
  • A<strong>B</strong>CとA <strong>B</strong> Cを同じ出力へ統合しない。
  • 空白だけのtext nodeをproject固有処理で削除しない。block間の整形はPrettierだけに委ねる。
  • 日本語本文を英単語と同じ方法で分割できると仮定せず、golden testで実際の出力を固定する。

5.3 Raw textとembedded content

  • pre、textarea、script、styleの本文をproject固有処理でtrim、dedent、escapeしない。
  • pre.mermaidのdiagram sourceを別formatterへ渡さない。
  • inline JavaScriptとCSSの整形は初期releaseの非目標とし、embeddedLanguageFormatting: "off"を固定する。
  • Prettier実行前にraw本文をsource内に存在しない決定的markerへ置き換え、実行後にmarker周囲へ追加された空白を含むinner range全体を元本文へ戻す。
  • markerが一意でない、消失した、複数出現した、またはmarker周囲に空白以外が生成された場合は内部errorとして変換を停止する。

5.4 Attributeとcomment

  • attributeの順序を独自にsortしない。重複attributeはFormatterで選択せず、既存HTML001を残す。
  • boolean attribute、quote、void elementの表現はPrettierのHTML printerへ委ねる。
  • body内commentの本文と相対順を保持する。
  • formatter ignore commentやproject固有directiveは初期releaseで導入しない。

6. Tag置換と自動修正の安全性

初期releaseで自動削除するtagはdocument envelopeのhtml、head、bodyと許可metadataだけである。本文tagの置換やwrapper削除は実装しない。

既存Lint ruleに対する初期releaseの処理
Rule 自動修正 理由
HTML001–HTML004 なし 壊れた構文、未知要素、標準構造、suppressionの正しい修正を一意に選べない。
DOC001 document envelope除去だけ article wrapperの新規追加やmainからの置換は別のcontent modelやscript selectorを変え得る。
DOC002 既存articleへのlang/dirコピーだけ sourceに存在しない言語を推測しない。
DOC003–DOC004 なし 題名生成、h1選択、heading level変更は文書outlineの意味を変える。
REF001–REF003 なし IDやURLの正しい参照先を推測しない。
A11Y001–A11Y002 なし 画像の意味やARIAの参照対象をFormatterが決めない。
FIG001、FIG101 なし caption本文生成とfigure範囲の決定には内容理解が必要である。
TBL001–TBL002 なし 表の目的、header cell、scope方向を内容から推測しない。
DET001 なし summaryとして使う本文を選ばない。
INT001–INT002 なし canvas名やMermaid sourceを生成しない。
INT101 なし 重要なdata tableを生成できない。
DOC101、SEM101 なし slug、section、aside、navの選択はstable IDと文書意味に関わる。

6.1 将来Fixerを追加する条件

将来のFixerはFormatter moduleへ直接if文を追加せず、rule ID単位のregistryにする。各fixは、入力のtext、comment、attribute値、node順、local URLを失わないこと、同じ入力から同じeditを返すこと、適用後に対象diagnosticが減り新しいdiagnosticが増えないこと、2回目にeditを返さないことをtestで証明する。 

interface FixDefinition {
  rule: RuleId;
  safety: "mechanical" | "safe" | "semantic";
  createEdits(context: FixContext): readonly TextEdit[] | null;
}

semanticはsource editを生成せず、LinterのdiagnosticをLLMへ返すだけにする。divからsectionへの一括置換、単一子wrapperの削除、空element削除は将来もdefault fixへ含めない。

7. 処理pipeline

  1. target pathをfileまたはdirectoryとして解決し、symlinkを除外してHTML fileをPOSIX相対path順に並べる。
  2. UTF-8でsourceを読み、BOMの有無を記録する。
  3. html-validate Parserを1回実行し、parse errorとtag eventのsource locationを収集する。parse errorがあればFMT001としてfileをblockedにする。
  4. 同じparse結果からfragmentまたはfull documentへ分類する。
  5. full documentなら4節の規則を検査し、安全ならbody inner sourceを切り出して許可attributeを移す。
  6. 固定optionでPrettierを1回実行し、format failureはFMT001としてblockedにする。成功時はLFとfinal newlineを確認する。
  7. 整形後sourceをlintDocumentへ渡し、残るdiagnosticをresultへ格納する。
  8. 元sourceとoutputをcode unit単位で比較してchangedを決める。
  9. project全fileのCore resultを確定してから、checkならreport、writeなら変更fileだけを書き込む。

初期releaseでは、Formatter出力に既存lint errorが残っていても、構文解析とenvelope変換が安全なら整形自体をblockedにしない。FormatterはLinterの修正完了を装わず、残ったdiagnostic件数をreportする。

7.1 Failure isolation

--checkは常に全targetを処理して、blockedとchangedをまとめて報告する。--writeは全targetのparse、normalize、formatが成功した後だけ書込段階へ進み、1件でもblockedなら1fileも書き換えない。書込段階では変更fileだけを順次更新し、unexpected I/O errorが起きた場合はそれまでに書いたfileと未処理fileをstderrへ明示する。

8. Core API

export type FormatInputKind = "fragment" | "document";
export type FormatStatus = "ready" | "blocked";

export type FormatProblemCode =
  | "FMT001" // parse-error
  | "FMT002" // unsupported-head-content
  | "FMT003" // unsafe-envelope-attributes
  | "FMT004"; // unsupported-envelope

export type FormatChangeKind =
  | "layout-formatted"
  | "document-envelope-removed"
  | "head-metadata-removed"
  | "envelope-attribute-copied"
  | "bom-removed";

export interface FormatProblem {
  file: string;
  line: number;
  column: number;
  code: FormatProblemCode;
  message: string;
  detail?: string;
}

export interface FormatChange {
  kind: FormatChangeKind;
  detail?: string;
}

export interface FormatDocumentResult {
  file: string;
  status: FormatStatus;
  inputKind: FormatInputKind;
  output: string | null;
  changed: boolean;
  changes: readonly FormatChange[];
  problems: readonly FormatProblem[];
  diagnostics: readonly LintDiagnostic[];
}

export interface FormatProjectSummary {
  files: number;
  changed: number;
  unchanged: number;
  blocked: number;
  lintErrors: number;
  lintWarnings: number;
}

export interface FormatProjectResult {
  documents: readonly FormatDocumentResult[];
  summary: FormatProjectSummary;
}

export async function formatDocument(
  source: string,
  absolutePath: string,
  relativePath: string,
): Promise<FormatDocumentResult>;

export async function formatProject(
  targetPath: string,
): Promise<FormatProjectResult>;

formatDocumentとformatProjectはstdout、stderr、process exit code、file writeを扱わない。outputはreadyなら必ずstring、blockedなら必ずnullにする。resultのarrayは相対path順、problemは位置とcode順、lint diagnosticは既存Linterのsort順にする。

8.1 Internal envelope model

interface SourceRange {
  start: number;
  end: number;
}

interface ParsedEnvelope {
  kind: FormatInputKind;
  bodyContent: SourceRange | null;
  htmlAttributes: ReadonlyMap<string, string | null>;
  bodyAttributes: ReadonlyMap<string, string | null>;
  headElements: readonly EnvelopeElement[];
}

source rangeはUTF-16 code unit offsetとして扱い、JavaScriptのsliceへそのまま渡せる値に統一する。lineとcolumnはuser向けproblemだけに使い、source editの境界計算には使わない。

9. LLM向けreport

9.1 Compact形式

docs/architecture.html
  C document-envelope-removed
  F layout-formatted
docs/unsafe.html
  4:3 E FMT002 unsupported-head-content — headのstyleを本文へ移してから再実行する
summary files=2 changed=1 unchanged=0 blocked=1 lint-errors=0 lint-warnings=0

unchanged fileは個別表示せずsummaryだけに含める。Cはcanonicalization、Fはlayout formatting、Eはblocked problemとする。既存lint diagnostic本文をformat reportへ全件反復せず、summaryの件数とspec-html lintを実行する案内だけを表示する。

9.2 JSON形式

{
  "version": 1,
  "mode": "check",
  "summary": {
    "files": 1,
    "changed": 1,
    "unchanged": 0,
    "blocked": 0,
    "lintErrors": 0,
    "lintWarnings": 0
  },
  "documents": [
    {
      "file": "docs/architecture.html",
      "status": "ready",
      "inputKind": "document",
      "changed": true,
      "changes": [
        { "kind": "document-envelope-removed" },
        { "kind": "layout-formatted" }
      ],
      "problems": [],
      "lint": { "errors": 0, "warnings": 0 }
    }
  ]
}

JSONへ整形後HTML sourceを含めない。source全体はtoken量が大きく、CLIのcheck/write結果として不要である。Core API利用者はFormatDocumentResult.outputから取得する。

10. CLI仕様

spec-html format [path] --check
spec-html format [path] --write
spec-html format [path] --check --reporter compact
spec-html format [path] --check --reporter json
  • pathの既定値は./specsで、HTML fileまたはdirectoryを受理する。
  • --checkと--writeのどちらか1つを必須とし、省略と同時指定をusage errorにする。
  • --reporterの既定値はcompactとする。
  • stdin、stdoutへのHTML source出力、glob、ignore file、config fileは初期releaseで扱わない。
  • directory探索は既存findContentDocumentsと同じ除外、symlink、sort規則を使う。
  • file指定は拡張子をcase-insensitiveに判定し、.html以外、symlink、directory内のnav.htmlと同名のfileを拒否する。

10.1 終了code

Format commandの終了code
Code 条件
0 checkで全fileがunchanged、またはwriteで全変更の書込が成功した。
1 checkでchangedが1件以上、またはmodeを問わずblockedが1件以上ある。
2 usage、path、read/write、dependency、予期しない内部処理に失敗した。

lint diagnosticが残っているだけではformat commandを失敗にしない。FormatterとLinterの終了条件を混ぜず、CIではformat --checkとlint --warnings-as-errorsを別commandとして連続実行する。

10.2 既存CLIとの互換性

  • 先頭argumentが正確にformatの場合だけformat parserへ渡す。
  • spec-html ./formatは引き続き./format directoryのViewer起動として扱う。
  • formatではViewer optionとlint optionを拒否し、Viewerとlintではformat専用optionを拒否する。
  • spec-html format --helpはformat helpを表示し、root helpにはusageを1行だけ追加する。
  • compact reportはstdout、usage、filesystem、write、内部errorはspec-html: prefix付きでstderrへ出す。
  • JSON reporterのstdoutにはJSON document以外を混ぜない。

12. File単位の実装task

taskはT0から順に行う。各taskは記載した対象以外を変更せず、確認commandが成功してから次へ進む。既存の未commit変更を破棄、上書き、再formatしない。

T0: Baseline、dependency、formatter spike

対象: package.json、package-lock.json。

  1. npm run typecheck、npm run lint、npm test、npm run buildを実行し、Formatter変更前の結果を記録する。
  2. npm view prettier@3.9.6 engines --jsonでNode.js 24との互換を再確認する。
  3. npm install --save-exact prettier@3.9.6を実行する。
  4. 一時test内でfragment、full document、inline whitespace、pre、scriptをprettier.formatし、固定optionがpublic APIで動作することを確認する。

確認: npm run typecheck && npm test。spikeで期待と異なる出力があってもoptionを増やさず、5節とfixtureの期待値を見直してから本実装へ進む。

T1: Formatter型とreporter

対象: 新規src/format/diagnostics.ts、新規tests/unit/format-diagnostics.test.ts。

  1. 8節のproblem、change、document result、project summary型を定義する。
  2. document resultをrelative path順、problemをline、column、code順にsortする。
  3. 9節のcompactとJSON reporterを実装する。
  4. detailを改行なし60文字へ正規化し、sourceやstack traceをreporterへ含めない。

確認: npm run typecheck && npm test -- tests/unit/format-diagnostics.test.ts。入力arrayの順序を変えてもsnapshotが一致すること。

T2: Prettier printer

対象: 新規src/format/printer.ts、新規tests/unit/format-printer.test.ts、tests/fixtures/format/fragments/、tests/fixtures/format/raw-text/。

  1. 5.1節の固定optionとformatHtml(source)を実装する。
  2. BOM除去、LF、final newlineをprinter境界で保証する。
  3. fragment、attribute折返し、inline whitespace、comment、entity、日本語、SVG、MathML、pre、textarea、script、style、Mermaidのgolden fixtureを追加する。
  4. 全golden fixtureで2回目のformat結果が同一であることを共通test helperで確認する。

確認: npm run typecheck && npm test -- tests/unit/format-printer.test.ts。

T3: Envelope parserと入力分類

対象: 新規src/format/envelope.ts、新規tests/unit/format-envelope.test.ts、tests/fixtures/format/documents/、tests/fixtures/format/blocked/。

  1. 固定HTML5 metadataを持つStaticConfigLoaderからpublic Parserを作る。
  2. parse:error、tag:start、tag:ready、tag:end eventでparse errorとexplicit html、head、bodyのsource rangeを収集する。
  3. implicit nodeとexplicit tagをlocationから区別し、3.2節のdocument分類を実装する。html外segmentはwhitespace、comment、DOCTYPEだけを許す小さなtrivia scannerで検査する。
  4. body inner sourceをoffsetでsliceし、body内commentとraw textが元sourceのまま得られることを確認する。

13. Test計画

13.1 Golden fixture

各fixtureはinput.htmlとexpected.htmlのpairにし、test source内へ長いHTMLを埋め込まない。意図を表す短いdirectory名を使い、1 fixtureで複数の独立条件を検証しない。

必須golden fixture
分類 Cases
Basic 単一article、nested section、list、table、details、aside、長いattribute。
Whitespace inline前後spaceあり/なし、mixed content、改行を含むlink、連続するphrasing element、日本語とcode。
Raw text pre、textarea、script、style、pre.mermaid、本文中の</body>風文字列。
Preservation comment、entity、Unicode、emoji、SVG、MathML、data URL、queryとfragment付きURL。
Document DOCTYPEあり/なし、title、複数meta、html lang、body lang、既存article lang、bodyにarticle以外のroot。
Blocked base、style、link、head script、未知head element、wrapper class/id/style、html外text、複数html、bodyだけ。
Invalid 未閉じquote、close order、duplicate attribute、壊れたcomment、invalid void content。

13.2 Property

  • Idempotence: 全ready fixtureでF(F(x)) = F(x)。
  • Determinism: target列挙順を変えてもdocument resultとreportが同じ。
  • No new diagnostics: lint-valid fragmentはformat後もdiagnostic 0件。
  • Raw preservation: raw text nodeのtext contentがformat前後で一致する。
  • Inline preservation:空白の有無を変えたpairがformat後も異なるDOM textを維持する。
  • Envelope isolation: body内のtag風文字列がbody rangeの検出に影響しない。
  • No partial preflight write: blockedを1件混ぜると全fileの内容とmtimeが変わらない。

13.3 Browser regression

代表fixtureをformat前後それぞれViewerで開き、見出し、link、画像、Chart.js、Mermaid、details、document titleを比較する。inline scriptは同じobservable resultを作ること、Mermaid sourceとfallback tableをJavaScript無効contextでも取得できることを確認する。Formatter専用のbrowser suiteを増やさず、既存viewer.spec.tsへ最小caseを追加する。

14. 受入条件

  • fragmentと定義済みfull documentを同じCLIから処理できる。
  • full documentの出力にDOCTYPE、html、head、body wrapperが残らない。
  • 危険なhead contentとwrapper attributeを黙って破棄しない。
  • 全ready fixtureでFormatterが冪等である。
  • lint-valid fragmentの整形後diagnosticが0件である。
  • inline whitespace、comment、raw text、scriptのregression testがある。
  • Core APIがconsole、process、file writeへ副作用を持たない。
  • checkはfileを書き換えず、writeはblocked時にpreflightで全書込を止める。
  • unchanged fileの内容とmtimeを変更しない。
  • compact/JSON outputと終了code 0/1/2がunit testとpack testで固定されている。
  • npm run checkが成功し、skipと未完了TODOがない。

15. 非目標

  • HTML以外のMarkdown、MDX、Vue、Angular、template languageを整形しない。
  • 利用projectのPrettier config、EditorConfig、ignore file、pluginを読み込まない。
  • JavaScript、CSS、JSON、Mermaidをembedded formatterで整形しない。
  • minify、HTML sanitization、script無効化、外部URL取得を行わない。
  • alt、caption、summary、table、heading、fallback contentを生成しない。
  • attribute、section、list item、table rowを意味や名前でsortしない。
  • semantic elementの置換、wrapper削除、空element削除を行わない。
  • 初期releaseではeditor integration、language server、watch mode、cache、parallel formattingを作らない。

16. 保守とupgrade

Prettierのpatch/minor/major upgradeはformatter出力の変更として扱い、dependencyだけを自動更新しない。upgrade時は全golden snapshot、repository HTML差分、browser regression、pack testを確認し、意図した変更だけを同じcommitへ含める。FORMAT_OPTIONSの変更も同じ手順を使う。

html-validateのupgradeではParser event locationとLinter diagnosticの両方を確認する。Formatterだけの都合でLinter ruleを弱めず、parser間の差が見つかった場合はinputをblockedにしてfixtureを追加する。

17. LLM実装時の実行規則

  1. 各task開始時に対象fileとbaseline testを確認し、前taskの未完了を次taskへ持ち越さない。
  2. 本書で固定したdependency、option、command名、終了codeを別案へ変更しない。
  3. 想定外入力を見つけてもheuristicを追加せず、blocked fixtureと明示的なproblemを追加する。
  4. Formatter実装中に既存HTML全体を手動整形しない。generated diffはT9へ分離する。
  5. golden expectationを実装結果へ無条件に合わせず、意味とraw contentが保存されていることを先に確認する。
  6. 既存testを削除、skip、緩和して完了条件を満たさない。
  7. 最終報告では変更file、実行command、test結果、残るlint diagnostic、未実装事項を明示する。
