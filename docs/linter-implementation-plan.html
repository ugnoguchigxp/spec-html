HTML document Linter 実装計画

本書は、Spec HTMLで扱うPure HTML fragmentを静的検査し、LLMと人間へ推奨される修正を少ないtokenで伝えるLinterの実装計画を定める。標準HTMLを独自DSLへ置き換えず、機械的に判定できる欠陥と、確度の高い改善候補だけを報告する。

1. 目標

  • HTML構文、文書構造、参照、accessibility、段階的強化に関する欠陥を、Viewerで開く前に検出する。
  • 各診断を、LLMが追加調査なしで修正へ移れる短い命令形にする。
  • 同じ原因から派生する診断を抑え、LLMへ渡すcontextを小さく保つ。
  • 標準HTMLの規則を再実装せず、project固有コードを検出と整形の薄い層に留める。
  • Document authoring principlesを自動検証可能な範囲で保護する。

1.1 成功状態

  • spec-html lint ./specsがcontent directory内のHTMLを再帰的に検査する。
  • 通常出力はfile単位にまとめられ、各問題が位置、severity、rule ID、推奨修正の1行で分かる。
  • 妥当な標準HTML要素をproject独自の許可listで制限しない。
  • docsとexamplesがerrorなしで検査を通過する。
  • 全ruleに、合格例、違反例、境界例の自動testがある。

2. Linter設計原則

  1. 標準優先: HTML Living Standardとaccessibility上の確立した要件を基準とし、独自要素や独自文法を導入しない。
  2. 最小制約: 正誤を断定できるものをerror、意味の改善を高い確度で提案できるものだけをwarningにする。
  3. 修正優先: messageは原因の長い説明ではなく、望ましいHTMLの形を命令形で示す。
  4. 一原因一診断: 構文崩れや参照元欠落から派生する二次的な診断を出さない。
  5. 決定的出力: file path、位置、rule IDの順で常に同じ並びにし、LLMが差分を比較しやすくする。
  6. 段階的強化: JavaScriptを使う表現でも、重要な内容をHTML本文から取得できることを検査する。

2.1 Severity

Severityの判定基準
表示 意味 終了code
E / error 構文違反、project契約違反、壊れた参照、明確なaccessibility欠陥。修正必須。 1
W / warning HTMLとして有効だが、より意味の明確な構造を高い確度で提案できる。既定では失敗にしない。 0

--warnings-as-errors指定時だけwarningを失敗として扱う。情報だけを出す第3のseverityは設けない。

3. LLM向け診断形式

既定のcompact形式はfile pathを一度だけ表示し、診断を1行に収める。messageは「違反している」ではなく「何へ直すか」を先に書く。

docs/sample.html
  1:1 E DOC001 root-article — 最上位を article[lang] 1個にする
  8:3 W DOC101 section-anchor — h2を含むsectionへidを付ける
summary files=1 errors=1 warnings=1

3.1 1診断に含める情報

  1. content rootからの相対file path
  2. 1始まりの行と列
  3. EまたはW
  4. 変更しないrule ID
  5. 短いrule名
  6. 推奨形を示す1文
  7. 必要な場合だけ、実際の個数や未解決の参照値

一般論、成功したcheck、source全体、stack trace、同じ修正説明の反復は通常出力へ含めない。

推奨修正messageは80文字以内、file見出しを除く診断1行は120文字以内を目標とする。上限へ収まらない理由、違反例、推奨例はrule registryへ分離し、通常出力には含めない。

3.2 Token量を抑える規則

  • file名を診断ごとに反復せず、file単位にgroup化する。
  • code frameと詳しい理由は既定で省略し、--explain RULE_IDで要求されたruleだけ表示する。
  • 同一要素へ同じruleが複数回成立しても1件にまとめる。
  • 構文解析が信頼できないfileでは構文errorを先に出し、誤検出し得る構造ruleを実行しない。
  • 既定の最大診断数を50件とし、超過時は省略件数と--max-issues 0による全件表示方法だけを末尾に示す。
  • 問題がなければsummary files=N errors=0 warnings=0の1行だけを出す。

3.3 JSON形式

--format jsonはeditorや他toolとの連携用とし、LLMへ直接渡す用途ではcompactを推奨する。JSONはschema version、summary、diagnosticsを持ち、message文字列の解析を必要としない構造にする。

{
  "version": 1,
  "summary": { "files": 1, "errors": 1, "warnings": 0 },
  "diagnostics": [
    {
      "file": "docs/sample.html",
      "line": 1,
      "column": 1,
      "severity": "error",
      "rule": "DOC001",
      "message": "最上位を article[lang] 1個にする"
    }
  ]
}

3.4 Rule説明とLLM修正loop

各ruleは、通常出力に使う短い推奨文に加え、--explain専用の理由、最小の違反例、最小の推奨例を1組だけ持つ。LLMは通常、次の短いloopで修正する。

  1. compact形式で実行する。
  2. errorをfile内の上から順に修正する。
  3. 修正方法が不明なruleだけ--explain RULE_IDで確認する。
  4. 再実行して派生診断が消えたことを確認し、warningを判断する。

このloopを成立させるため、rule ID、severity、推奨文はrelease間で不用意に変更しない。

4. Error rules

Errorは自動判定が安定し、修正しない限り文書の解釈、参照、または利用可能性が損なわれる項目に限定する。

HTML002known-element標準HTML、SVG、MathMLにない要素を使っている。内容に合う標準要素へ置き換える。
HTML003conforming-markup要素、属性、親子関係が標準HTMLのcontent modelに合わない。validatorが示す標準構造へ直す。

INT002mermaid-sourcepre.mermaidが空である。JavaScriptなしでも取得できるdiagram sourceを本文へ置く。

5. Warning rules

WarningはHTMLとして有効な書き方を禁止しない。意味を推測するruleは、誤検出が少ない限定的なpatternだけを対象にする。

初期releaseで有効にするwarning rules
ID Rule 検出条件と推奨形
DOC101section-anchorh2を持つsectionにidがない。安定したdeep link用のidをsectionへ付ける。
SEM101semantic-sectionarticle直下のdivが見出しと本文をまとめている。意味に応じてsection、aside、navなどを使う。
FIG101visual-figurecanvasまたはpre.mermaidがfigure外にある。図とcaptionをfigureでまとめる。
INT101chart-fallbackcanvasと同じsectioning範囲にdata tableがない。重要な値をHTMLのtableにも置く。

div、span、pの存在だけでは警告しない。sectionやtableの使用回数も評価しない。内容の意味をLinterが断定できないためである。

6. 検査engine

標準HTMLの構文、要素metadata、基本的な文書ruleにはhtml-validateを使用する。推奨presetを無条件に全適用せず、本計画に列挙したruleへ必要な標準ruleだけを明示的に有効化する。

Spec HTML固有層は、複数fileの参照解決、root article契約、Chart.jsとMermaidの段階的強化、診断の正規化だけを担当する。標準要素一覧、HTML parser、DOM実装をproject内で再実装しない。

6.1 検査順

  1. content rootを実pathへ解決し、既存navigationと同じ除外条件で.html fileを収集する。
  2. 各fileをfragmentとしてparseし、構文と標準HTML ruleを検査する。
  3. 構文が信頼できるfileだけにproject固有の文書ruleを適用する。
  4. 全fileのidと相対参照を集め、文書間linkとassetを解決する。
  5. 重複を除き、path、行、列、rule IDでsortして出力する。

6.2 Source構成

src/
├─ lint/
│  ├─ document.ts   # 1 fragmentの標準ruleとproject rule
│  ├─ project.ts    # file収集と文書間参照
│  ├─ diagnostics.ts # 型、重複除去、compact/JSON出力
│  └─ rules.ts      # rule ID、severity、短い説明
└─ cli/
   ├─ options.ts
   └─ main.ts

tests/
├─ fixtures/lint/
└─ unit/lint.test.ts

ruleごとにclassやfileを増やさず、同じ走査で判定できるruleは1moduleへまとめる。公開API、plugin API、設定loaderは作らない。

7. CLI仕様

spec-html lint [directory]
spec-html lint [directory] --format compact
spec-html lint [directory] --format json
spec-html lint [directory] --warnings-as-errors
spec-html lint [directory] --max-issues 50
spec-html lint --explain DOC001
  • directoryの既定値はViewerと同じ./specsとする。
  • 終了code 0は成功、1はlint error、2は引数、filesystem、内部処理の失敗とする。
  • 外部URLは存在確認しない。構文上有効なら検査対象外とする。
  • --explainはruleの理由、違反例、推奨例を表示して終了し、通常診断へ説明を反復しない。
  • --max-issues 0は件数制限なしとする。

repository自身の検査には、build済みCLIを使う次のscriptを追加する。

{
  "scripts": {
    "lint:docs": "node ./dist/cli.js lint ./docs && node ./dist/cli.js lint ./examples"
  }
}

checkではbuild直後にlint:docsを実行し、実際に配布するCLI bundleを検証する。

8. 実装段階

M0: Baseline固定

  • 現在のdocsとexamplesをrule候補で監査し、期待するerrorとwarningをfixtureとして記録する。
  • 各ruleが既存のauthoring原則から導けることを確認し、新しい文書DSLになるruleを除外する。

M1: 静的検査core

  • html-validateをdependencyへ追加する。
  • 4節のうちintegration固有のINT001とINT002を除くerror ruleを実装する。
  • 診断型、重複除去、決定的sortを実装する。

M2: Spec HTML integration rules

  • INT001、INT002と4個のwarning ruleを実装する。
  • 文書間fragment、asset path、content root境界を検査する。
  • 構文error時のcascade抑制を実装する。

M3: CLIとtoken効率

  • lint subcommand、終了code、compactとJSON formatterを実装する。
  • 50件制限、file group、summary、--explainを実装する。
  • lint:docsをcheckへ組み込む。

M4: 描画後検査

静的解析で確定できない項目だけを既存のPlaywright testへ追加する。通常のspec-html lintからbrowserは起動しない。

  • Chart canvasがaccessibility tree上で名前を持つ。
  • JavaScript無効時も重要な数値、caption、Mermaid sourceを読める。
  • 生成後のSVG、table、code blockがdocument幅を超えない。

9. Test計画

検証層と成功条件
層 検証内容
Rule unit test全ruleに最小の合格例、違反例、誤検出しやすい境界例がある。
Project test文書間fragment、asset、root外参照、重複ID、除外directoryを一時directoryで検証する。
Formatter testcompact出力をsnapshot化し、順序、group化、件数制限、summaryが安定している。
CLI test成功、error、warning、--warnings-as-errors、内部失敗の終了codeを検証する。
Repository testdocsとexamplesがerror 0、意図しないwarning 0になる。
Browser test静的解析では確定できないaccessibilityと非JS表示をChromiumで検証する。

rule追加時は、診断数だけでなく出力tokenの増加もreviewする。同じfixtureに対するcompact出力が冗長になった場合、messageの短縮かcascade抑制を先に検討する。

10. 完了条件

  • 本書のerror ruleとwarning ruleがすべて実装され、rule IDがtestで固定されている。
  • 1件の診断だけで対象位置、severity、推奨修正が分かる。
  • 50件以内の通常出力に長い説明、code frame、成功logが含まれない。
  • 壊れた1要素から同じ修正を要求する診断が連鎖しない。
  • npm run checkがLinter自身、repository文書、browser上の補完検査を含めて成功する。
  • Linterを通すためだけの独自要素、必須class、必須data-*属性が導入されていない。

11. 非目標

  • HTML Living Standard全体のvalidatorを自作すること
  • 文章内容の正しさ、十分さ、読みやすさを採点すること
  • section、table、header、footerなどの使用量を強制すること
  • div、span、pを一律禁止すること
  • 自動修正、対話UI、Viewer内の診断panelを初期releaseへ含めること
  • user定義rule、plugin、設定file、inline suppressionを初期releaseへ含めること
  • 外部URLへrequestして到達性を検査すること
  • 信頼できないHTMLを安全化するsanitizerとして扱うこと
